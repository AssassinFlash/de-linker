# Notification transport capacity

The 22 October incident filled the single 80-message ledger although internal messages actually used authenticated SMTP. The owner's hPanel readback confirms Starter Business Email allows 1,000 messages per rolling 24 hours; a read-only runtime check confirms both the configured username and verified sender match that mailbox. This is capacity evidence, not a delivery guarantee.

Initial operational allocation approved by the owner: SMTP 400/rolling day (40% of 1,000, leaving 600 for manual mail and other applications), PHP 80/day (80% of the shared-host 100), each 8/minute (the existing conservative allocation, no new provider minute claim). Of each daily allocation the final 10% SMTP (40) and 20% PHP (16) are reserved for critical producers. Ordinary traffic stops at 360/64 total attempts; critical traffic can use 400/80. These fractions are initial operational choices, not measured customer demand. Minute windows remain shared across priorities so a critical message may wait up to the next minute slot.

Trusted critical producers: native Woo password reset, WordPress password reset, staff account approval/restriction/rejection, issued Proforma, staff health/security alert, and a staff member's explicit single-record inquiry release. Internal inquiry, registration/VAT notifications, digest, customer acknowledgement, Genie/address/conversation mail and unrecognized producers remain standard. Subject, body, external headers and Jev decisions cannot promote priority. Staff release stores private job priority separately; original recipients, subject/body, headers and attachments remain unchanged. Optional receipts retain their existing 2/hour, 5/day per target and 10/day site admission caps.

The new ledger is serialized under a database connection mutex and read/written directly to avoid stale Redis option values. Its first initialization copies every valid unlabelled legacy timestamp into both transport pools without modifying the original option. Reservation checks and appends atomically before each actual transport attempt; failed sends are charged, never refunded. SMTP failure may attempt PHP only after its own atomic PHP reservation. Capacity waits retain the original job and failure count; actual transport failures retain the existing retry delays spanning at least 24 hours. When SMTP fails and PHP has no capacity, the original job retries SMTP at its normal failure delay and that channel's real next slot; PHP exhaustion does not unnecessarily delay a recovered SMTP channel. All locks are bounded; lock/database failure queues rather than sends without accounting.

A full existing PHP pool cannot immediately send account recovery from the unchanged de-linker sender through a different authenticated identity. It waits for the oldest actual timestamp to expire. Future reserved PHP slots protect those messages from ordinary traffic. No ledger reset, historical timestamp alteration, credential or visible sender change is part of this change. The 38 incident-held jobs remain held, before all capacity accounting.

Acceptance: native independent database connections compete for the last slot and initialization; historical migration occurs once; transport-specific failure/fallback, unavailable channels, critical authenticity, held zero cost, exact next-slot release, retry idempotence, local tester-only transport and static/CI checks. Deployment belongs to the coordinating root and requires readback of the preserved ledger and held jobs.

The final implementation adds two operational requirements from the coordinating incident review. A reservation commits in its own transaction before the actual transport. It cannot join a caller's WooCommerce transaction: an already active caller transaction causes a capacity wait and durable queue handoff instead. Read-only `next_slot` inspection does not initialize, mutate or prune a ledger, including staff release and future retry scheduling. The transaction guard uses `SET TRANSACTION` (next transaction only), which MySQL and MariaDB reject inside an active transaction; it never commits or rolls back the caller.

Saved inquiries pending verification or an explicit individual staff review are exposed by admission's trusted, read-only `linker_commerce_pending_review_summary` filter. The result is count, oldest saved Unix time and a native admin URL, or an explicit error. Confirmed campaign samples, erased/missing records, ordinary model uncertainty and incomplete admission reservations are excluded by the producer. A missing producer/error is not interpreted as zero.

The existing independent minute recovery triggers one aggregate reminder at the first tick, then at most one/hour while a batch remains pending, with a strict global 24/rolling-day maximum across batches. An existing queued/failed reminder job prevents new duplicates. This staff health message is a trusted critical producer, so it can use the SMTP reserve even when ordinary business messages reach 360; it never increases the 400 total. Every actual reminder transport attempt, including failures and retries, also has an independent atomic rolling-day ceiling: SMTP 24 and PHP 8. This leaves at least 16 SMTP and 8 PHP slots for other critical work when ordinary traffic has filled its allocation. The trusted reminder category persists on the original job and its tester-only transport copy; no public mail field/header can set it. Reaching the category ceiling preserves the original job and failure count until its true next slot. The daily digest also displays pending count and oldest age. No customer body, submitted URL or model label is included. Reminder generation is an Outbox handoff; only native transport success is logged as sent.

## Executable rollback and roll-forward

Prefer retaining this Mail budget compatibility layer when rolling other modules back. A complete source rollback must use the shipped commands while the new code is still loaded:

1. Take the normal local backup and record the existing held inquiries/jobs.
2. `wp linker-commerce mail-budget pause` installs a durable sending fence. Customer submissions and original jobs remain available. Already reserved attempts remain charged; no further reservation succeeds while paused.
3. `wp linker-commerce mail-budget rollback` atomically appends every unprojected real SMTP/PHP attempt to the old schema, preserving all existing timestamps and later records. It commits the projection IDs and both options in one owned transaction, reads both writes back and prints a safe receipt with `paused`, counts and the legacy hash. A failed/interrupted operation can be rerun; a retry after commit appends zero duplicates. Do not switch code if this command fails.
4. After the successful receipt, perform the coordinated old-code switch and its normal runtime readback. Existing holds remain held; do not force old mail jobs or reset quotas.
5. When restoring this version, deploy the new code first and run `wp linker-commerce mail-budget resume`. It imports unknown old-code additions into both pools conservatively before lifting the fence. It accepts natural expiry of old timestamps, preserves new records and refuses changes to still-live historical attempts.

The native rehearsal injects a failure into the second database write and proves both writes roll back; reruns, actual SMTP+PHP attempts, old-code additions, and an enclosing business transaction are covered. These commands do not send an email, release a held inquiry or clear a ledger.
