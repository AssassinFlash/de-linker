# Native solar runtime installation

This is part of the full unified workbench delivery. The accepted local PV
parameter controls and shared saved-revision starts are recorded under
`docs/acceptance/2026-10-24/548/pv-settings/`. Their isolated component evidence
does not install a new native service, migrate its project store, establish
live provider acquisition or accept the complete product.

## Launch protection and private provider contract

The service manager inspects the on-disk planning executable before allowing
it to open the existing project database. A private `worker_host release`
command reports the source/dependency runtime hash and code's storage version;
it does not read operator runtime policy, instantiate Workspace, migrate a
database or require service/provider/model credentials. Its envelope uses the
existing version-1 private lifecycle protocol.

Routine `serve` must refuse both an existing store with a different schema
version and a running HTTP/worker with a different executable runtime. This
refusal occurs before drain, stop, dependency synchronization of an existing
environment, service restart or WordPress option updates. An unversioned but
populated store is not treated as a new empty database. A verified recovery
point, quiescent old pair and explicit paired upgrade are required to change
versions. Never silently migrate simply to display new frontend controls.

Pure numerical execution and lifecycle commands do not receive provider
credentials. Only the explicitly configured weather executor receives
APIFY_TOKEN from its private process environment, together with the proxy/CA
variables used by the retained requests transport. Service and model secrets
remain excluded. The current token is never printed, sent as a command/query
argument, written to runtime JSON, published in the browser or copied into
source/evidence. Missing/malformed tokens fail before stopping an existing
pair; enabled-weather policy is explicit and no physical assumption is added.
The HTTP and Genie launches omit APIFY_TOKEN. Each execution imports its
declared project source root, including when an owned frozen release reuses
the already-synced matching interpreter environment.

An installed `planner/engine-release.json` selects only a direct child of the
same instance's `planner/runtime-releases`. It binds every source file and the
project/lock bytes by SHA-256, includes the complete HTTP/worker entry points,
rejects altered/missing/additional Python source and escaping paths, and reuses
only this checkout's retained environment. Routine serve verifies the selection
before lifecycle changes and does not sync that environment under an active
frozen release. Selection installation is an explicit paired-upgrade operation;
routine serve never silently selects current checkout source in its place.

The real Apify account and retained Actor/build must pass authenticated
readback before a live acquisition test. Read-only access proof is distinct
from starting an Actor and publishing a validated owned weather source.

## Installation and acceptance obligations

Before an actual upgrade, verify current PID/start identity, source/runtime,
configuration, registered ports, database schema and remote/local quiescence.
Retain a verified bounded recovery point and executable pair; freeze the new
source/lock/environment and explicit PV/weather resource policy. Then stop
the actual old pair, migrate transactionally, start the new HTTP/worker pair
against the same workspace, compare readiness identities and only then resume
admission. On failure restore the matching executable/configuration/database
recovery point rather than run an older executable on a migrated store.

Read back all existing project/revision/input rows and references, foreign
keys, runtime/task identity, provider journal and original weather bytes.
Exercise the native browser chain weather → explicit selection/save → PV →
explicit selection/save → energy with genuine sources and retained outputs.
EN/DE desktop/mobile and failure/retry/recovery evidence remain required.
Document and reclaim superseded executable carriers and redundant backups
under the current local-storage policy. Do not touch another session's stack.

No launch-protection, provider-access or isolated test result alone accepts
native installation, engineering accuracy, detailed roof/electrical design,
manufacturer/country eligibility, reports/BOM/PDF, site/commerce integration,
review deployment or production delivery. All remain in the same full goal.
