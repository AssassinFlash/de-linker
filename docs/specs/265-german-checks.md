# #265 German checks: one owner per kind of German text, enforced by CI

Authority: [issue #265](https://github.com/AssassinFlash/de-linker/issues/265), the audit's structural findings S5 and recommendation 4 (`docs/research/2026-10-17-i18n-audit/AUDIT.md`), the owner's 2026-10-17 German-only ruling and AGENTS.md §3 (vocabulary, Sie form, day-first dates). German problems are caught by gates, not by eye; the gates extend what already ran (`just i18n-coverage`, the banned-words grep, #263's address rule) instead of adding parallel systems.

## Ownership: the single owner of each kind of German text

| Kind | Single owner | What keeps it in its place |
|---|---|---|
| Plugin PHP/JS strings | The catalogs `plugins/*/languages/*-de_DE_formal.po`, regenerated by `just i18n-commerce <instance>` and `just i18n-tools` (msgstr is the only place a German plugin string is written) | `just german-copy` reads every active msgstr; `just i18n-coverage` keeps every live source message in the catalog |
| Script translation JSON (`languages/*-de_DE_formal-*.json`) | The .po, through `wp i18n make-json` — never hand-edited | `just i18n-coverage` (byte-for-byte regeneration, #302); `just german-copy` reads the JSON German values directly, so a hand-edit fails even without WP-CLI installed |
| Per-language LiveCanvas exports (`content/livecanvas/de/*.html`, `content/livecanvas/partials/de/*.html`) | The repository exports, installed by `present`; the migration never writes `lc_partial`/`lc_dynamic_template` (spec 9 revision 2026-10-15, spec 254) | `just german-copy` reads their human text and date formats; `just internal-home-urls` keeps their literal site hrefs German (`/de/…`) |
| Reviewed journal labels (`plugins/linker-commerce/content/journal-titles.json`) | The repository file (`de` values) | `just german-copy` reads every `de` value |
| Database content (pages, posts, products, term names, SEOPress meta, media alt) | Auto-translation (`TranslateOnSave`), which enforces `plugins/linker-i18n/data/banned-de.json` and the glossary at write time; hand-written German is preserved | The one list `banned-de.json` is shared: the translator enforces it (`Translation\Rules::banned_in`, PHP-tested) and `just german-copy` fails when the list is missing, unparseable or empty — losing it disarms both fences at once |

There is exactly one German banned-word list (`banned-de.json`) and one matching-semantic implementation per side (PHP `Rules::banned_in`, the Python port in `tools/checks/german-copy.py`). A second list is not created; a new word enters the shared file and both fences pick it up.

## `just german-copy` (`tools/checks/german-copy.py`)

Runs in `just check` and CI. Reads the German surfaces above and fails on:

- **Banned words** — the shared list with `Rules::banned_in`'s semantics: whole-word matches ignoring case, a trailing `*` matches compounds and inflections. `Warenkorb*`, `Einkaufswagen*`, `Katalog*` are the basket/catalog family; the pronouns `du, dich, dir, dein*, euch, euer*` are the du-form rule (German is written in the Sie form, locale `de_DE_formal`). Word boundaries keep `Dichtung` away from `dich`; attributes like `dir="ltr"` are markup, not prose, because template text is extracted (text nodes, `aria-label`, `title`, `placeholder`, `alt`, quoted shortcode labels — the coverage gate's own extractor). Known limit, owned by the Genie line (audit M5-3): du-imperatives without a pronoun ("Nenne mir …") are verb forms no word list catches; the live chip msgstr carries them and passes by design.
- **The blog article word** — `Artikel` with prefix semantics ("Artikel lesen", "Artikelkontext"; AGENTS.md §3, audit M3: the blog says Beitrag). Two allowances: the legal citation `Artikel <number>` (the reason the shared list itself does not carry the word — its `_source` documents the DSGVO case) and the SKU compound `Artikelnummer(n)` (the reviewed German SKU label; also the old grep's exclusion). `Katalognummer` gets no allowance on new German copy: it is a legacy data word `Materials` rewrites to `Produktnummer` at runtime.
- **English date formats** — German dates are day-first ("19. Oktober 2026", "29.05.2026"). Banned: an English month name next to a day number ("October 19", "19 October 2026", "May 29, 2026" — audit M1), an ISO date (`2026-10-19`) in prose, and in the German LiveCanvas exports a `date_format="…"` whose first token is not a day token (`d`/`j`); `d.m.Y` and `j. F Y` pass, `M j, Y` and `Y-m-d` fail.
- **The catalogue word** — the vocabulary rule the previous inline justfile grep carried, unchanged in paths and exclusions: no `catalogue`/`katalog` raw line under the plugins' content, template and language directories (SKU compounds and the legacy-redirects payload stay allowed).

Obsolete (`#~`) catalog entries are dead copy and skipped; the catalog header and the JSON metadata (revision date, generator) are not prose.

## `just internal-home-urls` — German export hrefs

The #263 gate (no `home_url( '/…' )` literal in plugin PHP) also reads the German LiveCanvas exports since #265: a literal internal href there must start with `/de/`. Dynamic targets (`{Field url}`, `[lc_wc_get_page_url …]`), fragments, `mailto:`/`tel:` and absolute or protocol-relative off-site URLs are free. This is audit M2's rule ("every internal href in the German templates must start with /de/") — the defect it describes (`/de/category/system-design/` linking to `/product/`, a 404) is gone from main; the gate keeps it out.

## What the gates do not check

General English residue in German copy (a full German-vs-English detector is the translator's job and fails open by design when a source has no baseline), database German (no repository files; the translator's validator plus the shared list own it), and the English face's own vocabulary and date conventions (out of scope by the 2026-10-10 parity rulings).
