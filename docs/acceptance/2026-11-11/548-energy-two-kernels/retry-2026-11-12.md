## 3. 找到并修复的缺陷：硬编码 ULP 允差绕过配置容差

### 3.1 现象

冬季 run 唯一失败项：

```json
{"code": "inventory_discharge_power", "passed": false, "unit": "kW",
 "at_interval": 164, "worst_violation": 2.831068712794149e-15,
 "allowance": 1.1102230246251565e-16, "arithmetic_allowance": 1.1102230246251565e-16}
```

残差 2.83e-15 kW，允差 1.11e-16 kW。而同一次 run 里另外 51 项检查的
`max_allowance = 1.1377601088018564e-07`（配置容差基数）。

### 3.2 根因

`inventory_charge_power` / `inventory_discharge_power` 传入了
`hard_allowance = ulp(a) + ulp(b)`，而 `record()` 在 `hard_allowance` 非空时
**完全替换**配置容差：

- `shared_dc_checks.py:62-72`（修复前）：`allowance = hard_allowance if hard_allowance is not None else absolute + relative*|scale| + arithmetic`
- `plant_energy_checks.py:85-89`（修复前）：`allowance = hard_allowance if hard_allowance is not None else absolute + relative*|scale|`

对比同族的 `single_ac` 内核：等价的"端子功率 = 库存推进功率"检查叫
`reference_charge_delivery` / `reference_discharge_delivery`
（`dispatch_checks.py:211-227`），走的是
`absolute + relative*|scale| + local_energy_roundoff/dt`，**基数 1e-7**，
没有"用 ULP 替换"的分支。

后果：同一物理恒等式，在 `single_ac` 里按 `1e-7 + 1e-9*scale` 判定，
在 `shared_dc`/`plant_ac` 里按 1e-16 判定。
`#1107` 记录的 `single_ac` 10 次执行最坏残差 3.37e-13 **远大于**本次冬季的 2.83e-15，
却全部通过——因为前者允差宽 9 个数量级。

**注意**：`single_ac` 也有自己的窄允差分支（`capacity_conserved_inventory`、
`reserve_conserved_inventory`、`usable_capacity` 用 `inventory_boundary=True`，
只保留算术项）。那些检查的语义是"库存不得越界"，与"端子功率等于推进功率"
不是同一类；本次不把这些一并放宽，只修被 hard 分支替换掉配置容差的那两条。

### 3.3 修复

第一版把 `hard_allowance` 一律"叠加"到配置容差——**这是错的**，CI 抓到了：
`test_joint_verifier_cannot_finance_microsecond_delivery_from_soft_stock_tolerance`
的第二个断言（`continuity_pv_kwh`）在加宽后通过了，而它必须失败。

原因是 `hard_allowance` 在两个内核里承载了**两种相反语义**：

| 取值 | 语义 | 例子 |
| --- | --- | --- |
| `0.0` | **身份**：任何差异即违规 | `continuous_axis`、`state_continuity`、`continuity_*` |
| `ulp(a)+ulp(b)` | **算术**：两操作数相减的舍入余量 | `inventory_charge_power`、`hard_window` |

把两者都加宽，等于允许"身份漂移在容差内"——那正是伪造账本要利用的东西。

正确修法是**把两种语义拆成两个显式参数**：

```python
def record(..., exact=False, arithmetic_allowance=0.0, ...):
    allowance = (
        0.0
        if exact
        else absolute + relative * abs(scale) + arithmetic + arithmetic_allowance
    )
```

- 原 `hard_allowance=0.0` 的 3 处 → `exact=True`（允差恒 0，行为不变）
- 原 `hard_allowance=ulp(...)` 的 4 处 → `arithmetic_allowance=...`（叠加，这是本来的意图）

`plant_energy_checks.py` 6 处、`shared_dc_checks.py` 7 处全部迁移，
`hard_allowance` 参数名从两个文件里消失，语义不再靠"传 0 还是不传"隐式区分。

### 3.4 修复不会放宽真实缺陷检测

现有两个测试断言的是**伪造账本**：

- `test_shared_dc.py:164`：`replace(real_tiny, before=EMPTY, after=EMPTY)` 冒充放电
- `test_plant_energy.py:761`：`forged` 用 ghost 库存冒充交付

这两种残差是**库存量级**（kWh），远大于任何 `absolute` 项，加宽到
`1e-7 + 1e-9*scale` 后仍然失败。测试实测通过（124 项内核相关用例全绿）。

## 4. `plant_ac` 为什么仍然是 0 次

不是没尝试，是确定性地不可执行。`plant_ac_parameters.storage_unit()` 在把
"无 PV 的电池 DC 路径"归约为 AC 包络时，必须先知道反向（电网充电）路径是否存在：

```python
if bridge.reverse_supported is None:
    raise EvidenceMissing("plant_ac_reverse_capability:" + unit_id, ...)
```

`reverse_supported` 来自逆变器的 `battery_grid_charging_supported` 事实。
生产实测（本次同会话、同池）：

```
inverters in pool: 42
inverters declaring any reverse/AC-charge fact: 0
  (检查 battery_grid_charging_supported / max_battery_charge_ac_power_kw
   / max_battery_charge_ac_current_a / battery_grid_charge_supported)

storage_unit("a", params, sha) -> EvidenceMissing plant_ac_reverse_capability:a
  public_details: {"constraint_id": "plant_ac_reverse_capability"}
```

**这是设计上正确的拒绝**：`plant_ac_parameters.py` 的注释写明
"An explicitly absent edge transfers zero energy. Identity here is its inactive
algebraic coefficient, not a device efficiency."——但如果连"该边是否存在"都不知道，
默认它不存在就是静默改变物理。拒绝优于猜测。

`shared_dc` 不受此限：`shared_dc_checks.py:310` 只在 `reverse_supported` 为真时才校验反向流，
所以 `None` 在 DC 路径上是合法的"未声明反向能力"。

### 解除条件

给任一逆变器补上 `battery_grid_charging_supported`
（`quantity_kind=documented_operating_function`,
`scope=grid_connected_battery_charging`,
`requires_local_grid_permission=true`）与 `max_battery_charge_ac_power_kw`。
一旦有该事实，`4107 + 1954 @ mps=6, BAT1` 的 DC 派生已经可用（本次已实证
`usable_window_kwh = 60.0`），`plant_ac` 即可在同一项目上直接跑。
这属于 Woo 设备数据（C 线），本线按硬约束不写。
