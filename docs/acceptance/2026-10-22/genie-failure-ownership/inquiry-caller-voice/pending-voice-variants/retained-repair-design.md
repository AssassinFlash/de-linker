# Exact editor checkpoints and real retained memory entries

The fd04 review adds three actual consumers: Restore parks a stale UI over a newer selected-copy revision; stale clear/pagehide consumes that newer revision; and a quota failure while editing restored durable data overwrites the other existing memory copy. All three are blocked source findings. The original fd04 source and independent red fixtures stay fixed.

Every mounted editor preservation, including empty clear and the beforeLeave invoked by Restore authorization, must use the original acknowledged editing cursor. It may rebase only the unchanged target entry over unrelated writes. A fresh same-owner record is read/recovery evidence, never replacement write/delete authority. Exchange must compare its displaced UI with that acknowledged checkpoint. An unchanged stale UI needs no new copy and may yield to the requested existing target while retaining the newer real version. Distinct already accepted UI bytes cannot be discarded when that CAS conflicts.

The existing window journal therefore retains an entry only at a demonstrated overwrite/conflict boundary: when a fallback would overwrite a different inactive memory copy, or when current accepted editor bytes differ from their acknowledged checkpoint while that actual copy has changed. The retained entry keeps its original scope/attempt, exact ancestor/copy cursor, record, and original durable counterpart. It is window-only and uses the same unsaved warning. There is no new persistent storage key, identity, owner, attempt, route or UI. A cursor flag identifies an existing retained memory entry by its exact original revision and complete record, rather than a random synthetic ID.

This is not a per-keystroke/revision history. Normal updates replace the currently selected copy as before. Identical retained content is reused. Only an existing distinct copy that would otherwise be overwritten, or accepted new UI bytes at an actual CAS conflict, is retained. The number of entries follows actual demonstrated conflicts and explicit branch selections; no invented unlimited versions or arbitrary numeric eviction cap may silently discard accepted data.

The existing Restore action cycles among the finite actual distinct copies, including the third state in the quota consumer: original voice memory, original durable data, and the user's edited unsaved durable data. Only fresh-authorized explicit exchange selects an inactive retained copy. Async writers keep selected-store plus exact entry/revision checks. Each retained copy preserves its own counterpart baseline. Successful Send/clear consumes only its selected exact version and a proven unchanged original counterpart, never another real updated or retained entry. Surviving versions remain available without a scope/attempt-wide tombstone hiding them.

Tests must prove three independent original fd04 reds, stale unchanged UI exchange, stale UI with additional accepted text, stale clear, three-copy real Restore traversal with PDF/reselection data, selected success/clear with remainders reachable, B blank/no transport, unrelated-attempt rebase, real same-copy conflicts, and honest read/write outage behavior. App keeps storage details in the existing shared modules. Default ordinary single-copy paths and model/native identity contracts remain unchanged.
