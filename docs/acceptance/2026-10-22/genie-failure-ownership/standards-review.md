## Independently reproduced findings

1. **P1 — Hero does not revalidate on visibility-only resume.** `src/hero/controller.tsx:213` installs focus/pageshow/pagehide and explicit identity listeners, but no `document.visibilitychange`. The provided-context branch of `src/genie/shared/useDraftContext.ts:46` deliberately installs no lifecycle listeners, so the expanded Hero has no alternate handler. Actual `startHero` consumer: A sends an ordinary question, its failure and original field are visible, the document becomes hidden, native principal changes to B, then the document becomes visible without a separate focus/pageshow event. The A field remains visible. The equivalent App/workspace case passes. Add the existing native revalidation on visible, checkpoint on hidden, and symmetric cleanup in the controller. Do not rely on every browser emitting a companion focus event. This proves the component event boundary; it does not claim that a particular real browser has already emitted that exact sequence in production.

2. **P2 — a new accepted editor is lost while another attempt is pending.** `src/genie/App.tsx:305` and the corresponding `src/hero/Hero.tsx:205` before-leave callbacks return whenever `sending.current` is true. The actual App field remains enabled after A1 enters model transport, and its change handler accepts a separate A2 editing owner. A→B revalidation skips that new editor's checkpoint, then the scope cleanup clears its text/files. The independently exercised App sequence retains neither a durable nor a scoped window copy of A2. Preserve the accepted editor independently of the pending A1 failure cursor. Do not put A2 into A1's record or let an A1 result erase it; include Close/pagehide and the Hero counterpart when fixing the shared cause.

3. **P2 — consuming a memory revision leaves its older durable version recoverable.** `src/genie/shared/ownedFailure.ts:539` delegates a memory cursor entirely to the memory store. Actual journal sequence: persist editing revision 1; update the same scope/attempt while `setItem` throws, retaining revision 2 in memory; restore normal storage; consume revision 2. Consumption returns true and a window-only `consumed` set hides revision 1, but after rebuilding the window runtime with persistent storage intact, revision 1 is selected again. Process the precise same-attempt durable counterpart with raw/revision checks when possible, retain unrelated attempts/principals, and accurately propagate an unsuccessful durable cleanup. A window tombstone cannot establish reload persistence. This is a stale recovery/consumption defect, not evidence of cross-principal disclosure.

The first two editing/consumption findings were sent to the parent and producer as soon as their actual-module probes failed. The Hero visibility finding was independently reproduced here and also identified by the parallel Spec review; it is one defect, not two findings.
