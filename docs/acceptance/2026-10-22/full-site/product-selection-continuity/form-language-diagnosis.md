## Confirmed cause and existing evidence

`Presentation/LanguageLinks::toggle()` and `footer()` output ordinary anchors with `data-linker-language-choice`. The destination is rebuilt from the server's current request and Polylang's page/term mapping. `SelectionContext::language_query()` carries a revalidated public source and the original URL selection to its target-language counterpart. It has no access to the live message, edited topic, consent or inclusion checkbox.

The only in-repository frontend listener for `data-linker-language-choice` is `assets/legal-navigation.js`. It retains an existing legal section hash; it does not checkpoint any form. `assets/account-ui.js` handles submission busy states, password matching and registration steps. `src/protection/forms.ts` warms proof on interaction and gates the native submit. Neither saves editing state before language navigation.

The parent's existing [EN excluded frame](cua-final-20261022T0440/en-1440-excluded-keyboard.json) records a nonempty question containing a backslash, `selection.checked=false`, and target-language hrefs that still carry the original public context. The following [DE diagnostic](cua-final-20261022T0440/diagnostic-de-1440-language-discards-edit.json) records an empty question and `selection.checked=true`. These are actual 1440×1000 records at 04:52:04Z and 04:54:12Z. They support loss of the edited question and exclusion state; they are not a claim that every other form has been browser-reproduced.

The current native `Integration/ContactNavigationTest` proves archive → Contact → other-language Contact for the **initial URL selection**, including encoded punctuation and translated public sources. It asserts the initial checkbox is checked. It never edits the form or unchecks that checkbox before navigating. `Contact/FormTest` and `Integration/ContactSelectionTest` prove failed-POST recovery, exclusion, request UUID, normalized fingerprint and isolated queue metadata. They do not prove an unsubmitted language switch. These are separate consumers and must remain separate acceptance claims.

## What can be reused, and what cannot

`FormRecovery` already provides bounded contact field extraction, current Woo-session storage, escaping on render, validated selection JSON and a five-minute retry lifetime. Its special handling preserves structural JSON backslashes and URL percent escapes. `FormFields` carries the logical UUID into failed-submit retries. `Submission::from_post()` and `Business` produce the normalized protected payload; the selection is a separate private property and is added to the Contact fingerprint only when included. These should remain the authoritative schemas and actual send consumers.

The **current recovery operation is not an editing-draft store**. It has one key per action, consumes before the new page is complete, has no editor ID/revision or tab discriminator, and preserves a validation/submission request UUID. Reusing `save('contact', …)` on every language click would collide with failed POST recovery and other tabs. Inquiry has a different flash store; generalizing its error keys would incorrectly invent validation failures during navigation.

Woo already retains saved product quantities across locales; no cart reconstruction or order write is needed. Its guest session can move into a customer session on login (`Account/SavedSolutions` documents and consumes that behavior). Native Woo session membership alone is therefore insufficient to promise that private A text can be automatically shown after a principal change. `Protection/Identity::binding()` is a browser/account **budget binding**, not a WordPress login-session epoch. It deliberately survives relevant budget changes and omits the auth token; it must not be promoted into a new private-draft identity authority. `Account/AdminAccessNotice` is an existing example of using `wp_get_session_token()` and `WP_Session_Tokens` for a decision tied to the current authenticated session.

There is no reusable language-save API or universal draft binder in the inspected source. A new small form-draft adapter is necessary; a second model route, custom identity endpoint, ownerless sessionStorage/localStorage cache, browser `window.name`, proof reuse or private query string is not.

## Recommended native seam

The smallest durable design is a **navigation-only branch of the existing native form transport**, backed by a distinct Woo-session editing record. This is a proposed implementation, not existing behavior.

1. Keep `LanguageLinks`/Polylang as the one public destination resolver. On a recognized editable-form surface, associate both header and footer language controls with the same actual form, using a native language submitter and `formnovalidate`, styled through the current LC/WindPress classes. Other pages keep ordinary anchors. Changing language must not require a complete valid Contact/registration/password form. It must also not masquerade as the native Send/Register/Login submitter.
2. Add an early `language_handoff` branch **before** the existing Contact/Inquiry business processing and before Woo's corresponding form handler. It validates the source-bound native nonce/session and only the recognized target `en`/`de`, extracts a per-form whitelist, checkpoints it, then returns a 303 to the server-resolved paired page/endpoint. It never calls `Handler::process()`, `Business::run()`, VIES, account registration/authentication/save, password reset, inquiry creation or mail. Woo native callback order and action detection must be verified against the installed Woo version before selecting the hook; source presence alone is not this proof.
3. A small first-party enhancement can collect the **known** disabled registration pane and any other registered secondary editing surface into a typed navigation envelope. Do not use an unrestricted `new FormData(form)` dump, or turn every field into a hidden value. The existing native form may carry credentials to its existing HTTPS endpoint as it normally does; the early branch must never copy passwords, reset credentials, nonce/proof, bot clocks or entire transport bodies into a draft or a different channel. No new identity/model/mail request is needed.
4. Render the target form with its own fresh nonce, proof/widget state, page locale and native source data. Read the exact matching editing record before customer/default/URL prefill. User prose is not translated or sanitized into a new meaning; only labels and current public source metadata are localized. The form remains editable and requires its ordinary explicit submit. Quantity, account or engine changes remain independent explicit actions.

A generic click interceptor that saves asynchronously and follows the old anchor immediately is insufficient: it can lose the race, leave source inputs behind on an error, or send a stale snapshot after a later edit. If anchors are retained as the enhancement, they must prevent navigation until a checked native checkpoint has completed and leave the source page intact on failure. A separate REST draft API would duplicate more transport/error/identity work than the native branch and is not the first choice here.

Native submitters outside a form can be associated through the standard `form` attribute; do not nest forms in the header. The renderer needs a stable recognized form ID and schema, not an arbitrary selector. Actual header/footer geometry, keyboard behavior and native POST data must be checked. No-JS support is only established once that native branch works. If multiple independent forms contain changes on one page, preserving only the primary form is **not** a whole-page solution: the enhancement must checkpoint all registered dirty surfaces or require an explicit decision without discarding one. A no-JS multi-form fallback also needs a deliberate contract; this diagnosis does not claim one is already present.

## Required owner, state and failure contracts

| Boundary | Concrete requirement |
| --- | --- |
| Source owner before private bytes leave | Validate the source-rendered native nonce against the current authentication session. Guests also need the existing signed Woo guest session bound at form render; a shared user-0 nonce alone cannot distinguish two guest sessions. If a form has no native guest session yet, initialize that native session for the form or refuse the preserving operation explicitly; never infer ownership from user ID 0, the target language or a fresh B response |
| No new identity protocol | Derive the private owner comparison on the server from verified Woo guest session or current WP user + actual WP session token. HMAC it privately; do not expose raw cookies/tokens or call `Protection/Identity::current()` to create a new budget identity merely for navigation. Reuse the existing native owner/session; no custom browser credential or identity lookup is proposed |
| Caching | Guest-scoped source nonces and restored PII require private/no-store form responses. They must not enter shared page caches, public query logs or HTML cached for another session. This has a real Contact-cache cost to measure; do not emit owner-bound fields into a public cached page |
| Record shape | Separate from failure flash: version, form/schema ID, original native owner binding, random editor/draft ID, revision, explicit route/target, editable values with presence, created/expiry, and whether a protected operation has already been attempted. Keep public selection separate from private question and include an explicit inclusion enum |
| Multi-tab and interrupted navigation | Per-editor records, exact revision comparison, exact readback and exact consumption. Never one `contact` slot for all tabs. Concurrent revisions cannot overwrite or delete each other. An opaque handle may select a record only if necessary; it carries no PII and grants no access. Server owner verification remains required. Do not consume the sole recovery copy before the target render succeeds |
| Meaning of empty | Preserve intentionally cleared strings, unchecked consent and excluded selection as explicit values. Do not treat empty as “fall back to saved customer/original URL.” Exclusion cannot be represented by an omitted checkbox alone in the editing envelope |
| Contact selection off | Translate the canonical Contact target without reintroducing the selection query; persist the data-free excluded state. Target rendering shows the existing excluded feedback and no selection FIELD. A later ordinary form submit must have no selection metadata/fingerprint component, no hidden selection JSON, and no source query carrying the excluded selection into team records |
| Contact selection on | Reuse `SelectionContext` source revalidation and existing public-language mapping on the target; never trust a stored title/HTML. Preserve current message bytes independently. Deleted/unavailable source shows the existing clear exclusion option without erasing the message |
| Request UUID / fingerprint | A language checkpoint creates no admission reservation and uses no send allowance. Never reuse proof, widget acceptance or submitting state. A never-dispatched request may retain its logical UUID. After a real attempted protected operation, locale and localized selection can change normalized payload/fingerprint; do not mutate the old operation under the same UUID or mint a new UUID before resolving an unknown/completed operation. Preserve its retry/recovery route and require an explicit new-operation decision where semantics changed |
| Source still editing during save | Snapshot version and source owner before checkpoint; late completion must not clear new source input, navigate after a newer language choice, rebase A onto B, or acknowledge a different editor. Restore conflicts must keep the newly typed text and the old recoverable draft |
| In-flight business submit / draft AJAX | Do not stage or navigate through a native inquiry/order/account submit already dispatched as if it were an unsent draft. Respect existing draft-busy handling and resolve the original operation; language change cannot send a duplicate inquiry or consume a later revision |
| Failure or missing session | Explicit loading/retry in the current form and retain its input. No false saved acknowledgement and no automatic navigation. If the session/checkpoint cannot be persisted/read back, a memory-only claim is not cross-page preservation. Missing/expired/mismatched record must not silently re-check the old URL background or reveal another owner |
| Back/forward, refresh and repeated EN↔DE | Route pair and editing record stay separate from validation-error/success URLs. Keep current editor/revision reachable until successful business submit or explicit discard. Rapid switches, bfcache and stale callbacks cannot resurrect an excluded selection or overwrite a later draft |
| Files, speech and secret fields | The Contact native form currently has no attachment input. Do not add one here. Registration/login/account passwords and reset keys stay outside drafts and need re-entry where a page reload clears them. Tool file bytes/voice sessions use the tools' own ownership contract, not this native-form adapter; no automatic microphone, picker, model or calculation |
| Existing receipt and failure views | Do not turn a sent receipt into a blank editing form. Do not recreate an old failed-submission error merely to preserve inputs. Restore draft values after safe shortcode/template assembly so text cannot execute shortcodes; retain structural JSON/backslash handling |

The existing five-minute `FormRecovery` lifetime is a documented failed-submit value, not evidence for an arbitrary site-wide editing lifetime or record count. If reused for a one-navigation handoff, state that bounded purpose and make expiry visible; do not silently erase an accepted longer editing workflow or invent caps to make tests pass.

## Meaningful verification before implementation can be accepted

- Red/green actual header and footer controls: Contact EN→DE and DE→EN with incomplete fields, intentional blank text, multiline/backslash/percent/quote prose, changed topic/consent and included/excluded context. Assert actual target DOM, current FormData and then isolated native POST/order/queue metadata; a link/event spy alone is insufficient.
- Guest, current logged-in session, logout, guest→login, account A→B, same account with a new auth session, missing/expired cookies and cached-source HTML. No old private text or files may be shown or sent under a different owner. No new custom identity request is allowed.
- Actual registration both steps, including already-filled but disabled pane controls; incomplete native form must still switch; active pane and nonsecret fields survive; passwords/proofs/nonces/submitter commands never appear in the recovery record. Login/reset/account/address adapters must prove zero authentication/account/VAT/reset side effects from the navigation branch.
- Inquiry left editing plus right draft: committed lines remain native; typed quantity and message do not overtake or duplicate a draft/business submit. Validate same-UUID unchanged retry versus changed locale/payload and an interrupted result acknowledgement using existing `BusinessRecord`/ledger semantics.
- Two tabs, two forms, rapid switches, failure before/after checkpoint acknowledgement, readback mismatch, rejected cookie, server outage, stale revision, modified source while awaiting, refresh/bfcache and source-open-in-new-tab. Preserve the original and later editors; no automatic business send or implicit profile/draft write.
- Real EN/DE × 1440/390 keyboard/pointer journeys and per-state screenshots. Verify 44px controls, focus, error/retry exits, scrolling and context visibility. Keep native successful/failed POST, no-JS behavior, tool-owned drafts and browser visual evidence separately named.
