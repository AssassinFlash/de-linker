# Ordinary Genie draft and failure ownership — design candidate

Status: the base design and final EN/DE warning passed independent Spec and Standards review. The added scope/attempt bucket clarification has Standards PASS and awaits narrow Spec confirmation; implementation and production acceptance remain pending. This follows the confirmed local consumer defect in `genie-failure-isolation-discovery.md`. Marketing Batch A remains a separate frozen candidate.

## Existing pattern and scope

Use the existing native WordPress REST authentication and Genie browser epoch. `Conversations::entry_scope()` already returns a private, non-cacheable opaque comparison value for this browser tab and native authentication session. A scope grants no conversation permission; `Conversations::may_use()` continues to own that permission. Logout rotates the guest epoch. The established marketing recovery code supplies fresh verification, exact-record CAS, recovery barriers and explicitly parked drafts. Ordinary text must not be labelled as a marketing entry to reuse these protections.

The repair covers ordinary workspace, dock and homepage input, dictation, prepared image/PDF files, pending/failed turns, Retry, reload and movement between surfaces. Marketing entry IDs and provenance remain separate optional metadata. No model route, inquiry/notification path, product fact or native conversation claim is changed.

## Owner and initialization

Introduce an independent failed-draft owner consisting of an opaque native scope and a stable attempt identifier. All new failed-draft producers supply an owner; only a legacy parser may encounter ownerless bytes. A retry retains the attempt owner. Editing an owned recovered question retains its owner until an explicitly resolved replacement creates the next attempt. Conversation IDs, when available, are checked through the native authority and never used as proof for an ownerless old record.

Ownership must precede user bytes. On an empty newly mounted ordinary composer, resolve the current scope before enabling input, attachment capture or dictation. Prefetch quietly; the un-interacted homepage Hero retains its exact existing appearance. Only an explicit interaction opens the existing loading presentation. Its field is visibly unavailable and cannot claim to have accepted text; focus stays in an actionable loading/retry region, without jumping into a hidden field. Retain the initial attachment/nameplate/voice intent and resume the appropriate customer-controlled action after verification, without automatic microphone capture or a model turn. On failure, keep the composer unavailable with an existing reviewed error/Retry control; do not accept text and later assign whichever identity happens to answer. A customer can retry this auxiliary lookup without starting a model turn. Do not silently block a visible enabled Send. Browser fixtures must demonstrate the first interaction and typing/IME/attachment/voice transitions, including that no accepted input is lost.

Once a composer belongs to A, a later scope response for B cannot rebind its current text or files. A fresh verification immediately before actual transport follows queued thread/metadata reads. Re-entry, pageshow/focus and known login/logout or native authorization failures trigger renewed verification before recovering cached content; pending verification must not expose unverified cached bodies or filenames. Exact event handling and stale-response protection require consumer fixtures rather than an assertion that all identity changes are observable instantly.

The barrier covers already mounted textarea values, visible filenames and hidden prepared bytes, not only storage hydration. On revalidation, quarantine their UI until the owner is confirmed. Each async model/prepare/retry callback captures its owner and epoch. After identity invalidation or a newer epoch, success, refusal, conflict, error and finally are all stale: they cannot paint the old text/files, clear another owner's state or unlock its send barrier. Native transport cancellation is useful but does not replace this settlement check.

Increment the context epoch on native New/Select/Delete conversation, invalidation of the active conversation and surface unmount, even when the principal remains the same. Reuse current history/continueConversation lifecycle boundaries; a stable attempt ID does not permit a response to paint into a different thread. A conversation ID still cannot prove ownership of unknown v1 bytes.

Scope initialization must work when sessionStorage itself is unavailable. Prefer the existing persisted tab ID. If its read or first write throws, share one random in-memory tab ID across the whole window and both bundles, and use the same native server principal check. This changes no authorization or cookie authority. In that mode, do not consume or claim any old persistent recovery record and do not promise reload recovery. Do not let the failed TAB_KEY write prevent reaching a verified, usable memory-only composer. Fixtures cover no pre-existing tab key with getItem and setItem failing separately, stable memory tab identity across Hero/dock, fresh native identity verification, current-mount Send/Retry, and untouched old unknown v1 bytes.

The two separately built bundles also share the in-progress initial scope lookup across the window, together with its bootstrap generation. A module-local promise map is insufficient for newly added parallel quiet prefetch when the guest epoch cookie is not yet established. Coalesce only that cold bootstrap; known identity/lifecycle invalidation rejects its stale result. This is not authority caching: Send/Retry's fresh verification still issues a new native lookup after queued thread work. Exercise the actual two-bundle cold-guest bootstrap and separate storage exceptions, proving one stable initial native scope and independent later fresh checks. Retained attachment/photo/voice modes resume through the existing explicit Choose/Dictate action after verification; do not call a file picker after an async wait as though the initial user activation still existed, or start a microphone automatically.

## Legacy bytes

Unknown ownerless v1 records have no reliable account, conversation or attachment provenance. They are not automatically migrated, displayed, combined with a new draft or retried. Preserve their original storage bytes inactive for the remainder of the tab lifetime. Do not copy potentially large base64 records into a second key merely to quarantine them, infer an owner from matching text/empty history, or overwrite their old key with a new failure.

Use a new versioned namespace for new independently owned records; old unknown bytes stay at the old key untouched. The single candidate selector prefers an existing valid new-version record for the freshly verified current owner. Only when no such new-version record exists may it nominate a structurally scoped old marketing record for fresh verification and exact migration; the migrated write must read back before removing exactly the old bytes. Ownerless v1 is never a candidate. If scoped v1 and current-owner v2 coexist, v2 is the active candidate and v1 stays inactive; two automatic restorers must never race to write their separate candidates. A generic restoration notice may explain the inability to verify an older draft, without printing its content or filenames; any new sentence requires the existing EN/DE copy review.

The versioned namespace is not a single replaceable failure slot. Partition it by opaque native scope and retain records by stable attempt within that owner's bucket, with an explicit active attempt. Resolve fresh native scope before reading that scope's bucket; a key or digest only locates data and does not prove ownership. A failure created by B must leave inactive A bytes unchanged rather than replace them. New attempts also do not silently erase the same owner's unique older attempt. Only an explicit successful resolution, abandonment or durable exchange may consume the corresponding attempt; do not add an unsupported quantity limit, TTL or automatic eviction. Returning through the same still-valid native scope may recover its own record; a later login with a rotated native scope must not reclaim an inactive old bucket merely because the account is the same.

Consuming the active attempt must maintain a valid surviving candidate in that same CAS. Keep explicit insertion order and select the newest surviving attempt; opaque ID lexical order and client-clock guesses are not ordering authorities. Retained attempts must remain reachable through the existing explicit Restore action, without requiring a new multiple-draft UI. The consumer counterexample is A1 failure→A2 failure (active A2)→A2 success/abandon→fresh mount and fresh native-scope verification→explicit recovery of A1. Late A2 cleanup cannot remove A1 or replace a newer active attempt. A suspended or missing active pointer cannot silently strand preserved records.

Unsent ordinary input accepted while A was verified also remains A's draft. Before revalidation quarantine, Close or a thread change removes that editing surface, retain its current text and attachments under the immutable original owner and stable attempt as an explicit v2 `editing` state. After B is confirmed, A's content and filenames cannot appear or be sent through B. Fresh verification of the same original still-valid A scope permits the existing explicit Restore action to restore an editable question, without a false model-failure state, marketing entry ID or automatic turn. A new login with a rotated A scope still cannot reclaim the earlier scope's data.

An editing persistence/readback failure retains the original-owner object in isolated window memory; it cannot authorize changing the draft's owner to B, acknowledge durability or promise reload recovery. B cannot inspect the A memory draft. When the original valid A restores it, show the already reviewed memory-only warning. Add actual consumers for unsent A text/PDF→B blank/no payload→fresh original A→explicit Restore to ask, Close/reopen and thread-change retention, and storage failure without B disclosure or false persistence. Unknown ownerless v1 remains inactive and untouched.

CAS compares the current scope bucket's exact expected raw bytes and target attempt/revision. A late A callback cannot mutate B or remove other A attempts; cleanup cannot remove a nonempty bucket. Both bundles use the same synchronous arbitration boundary, with no asynchronous wait between comparison and write. Distinguish a failed getItem from an absent record: a failed read is not permission to overwrite. A failed write/readback cannot acknowledge persistence, clear the source or announce success. Add consumer counterexamples for A failure→B failure→return to the original valid A scope, a late A cleanup, two same-scope attempts and separate get/set exceptions. The original unknown v1 bytes remain unchanged in every case.

The current producer census is App ordinary/entry-derived Send and Retry, Hero Send and Retry, App/Hero hydration reconciliation writes, and useFailure's commit/attachment-reconciliation paths, including answered/abandon/settlement cleanup. All new writes and clears go through the unified versioned-key/owner/attempt boundary, including marketing turns. The homepage controller and verified-failure helper are readers of that same selector; they do not retain a second automatic v1 recovery path. Re-run this census across actual source before claiming complete producer/reader coverage.

Storage quota failure does not authorize deleting unknown old content. Preserve the current in-memory owner and show the existing explicit file-reselection limitation when bytes cannot be retained. No apparent success/acknowledgement is emitted before durable write/readback where the operation promises reload recovery.

If even the minimal text-plus-owner record cannot be stored, enter explicit memory-only mode: the verified current draft remains editable and may be sent/retried in the current mounted session, but cross-surface/reload recovery is not promised. Do not clear another durable candidate, emit a persisted ACK or display a saved state. Show a reviewed warning that refreshing or leaving can lose this unsaved question; file-specific reselection copy alone is insufficient. Reviewed final copy: EN “This question could not be saved. It may be lost if you refresh or leave this page.” DE “Ihre Frage konnte nicht gespeichert werden. Wenn Sie diese Seite neu laden oder verlassen, kann sie verloren gehen.” The warning must be paired with working in-memory retry and cannot appear as a false successful recovery. A warning alone does not authorize losing the source during a cross-surface transfer: no durable acknowledgement means the source remains the owner.

Copy review record: initial EN asked the customer to keep the page open; initial DE used “zum Senden oder erneuten Versuchen”. Independent Spec review found the refresh/leave risk merely implicit and the German wording awkward. Standards separately asked for the refresh consequence and removal of the internal tab-storage detail. The final pair above incorporates both comments, states the consequence directly and uses formal Sie. This is reviewed product copy for the next implementation, not a claim it is currently rendered.

## Asynchronous write boundary

| Situation | Required result |
|---|---|
| Mount waits on scope/history, then new input or files appear | Do not overwrite the newer editor or unique older failure. Resolve ownership first; explicitly restore or park before releasing Send. |
| Scope temporarily unavailable | Preserve the safe owned record; do not render an unverified cache. Retry remains visible and does not create a model turn. |
| Scope confirms another identity | Do not render or transport the old owner's bytes. Do not delete a superseding record. Release only the barrier belonging to the resolved old record. |
| FileReader/prepare is busy while recovery completes | Keep the current editor intact; the older owner remains durable and recoverable. Preparation completion must leave an actionable recovery control. |
| Customer chooses Restore while a different editor exists | Write/read back the displaced editor under its verified owner before replacing it. Preserve omitted/reselection names through both directions of exchange. |
| A delayed turn or recovery completes after a newer attempt | Exact record/attempt comparison prevents it clearing or rewriting the new owner's failure. |
| A model or FileReader response for A arrives during verification or after B is confirmed | Quarantine old mounted values/chips/bytes. Every settlement branch checks the captured owner epoch before changing UI, storage or send protection. |
| Retry after empty or forbidden history | History shape is never proof of ownership. Validate both display and the final prepared transport payload, including hidden files. |
| Auxiliary identity changes during a queued lane | The final fresh check fails closed; do not reuse the earlier cached response as authority. |

All three actual surfaces share the owner contract. A hook-only test is insufficient if the real homepage controller does not mount the hook or render its recovery control.

## Acceptance before release

1. Begin with actual ordinary typing/dictation/file preparation and real failure-reducer writes, without entry binder or fabricated marketing metadata. Repeat the twelve established diagnostic consumers as regression assertions that private text/files are neither shown nor transported under B/guest.
2. Verify same-owner recovery, in-place identity change, reload and cross-surface movement; 200 empty/403 history, initial pending, temporary scope failure, FileReader pending, superseded records, failed durable writes, missing-only drafts and both directions of explicit Restore. Exercise an in-flight model/prepare request returning after A becomes B for each success/refusal/conflict/error/finally branch. Verify unknown v1 plus a new failure, scoped v1 plus v2, a late old reader, and old unknown large bytes causing the minimal new write to fail. The test seam must name mocked model/history/identity responses.
3. Verify all new producers write an independently owned version and every reader validates before rendering filenames/body. Unknown legacy bytes remain byte-identical and inactive while a new question can use the new key. No hidden PDF can enter Retry.
4. Review source against this design and repository standards independently. Rebuild/catalog checks, actual EN/DE1440/390 browser states and manual screenshots remain separate gates. Run affected native history, marketing entry and document-card regressions after the shared failure change.
5. Before production, retain the required local backup and rollback release. Production-safe readback may use only owned test text/files and accounts; do not create real customer inquiries, registrations or mail. Verify the installed bytes and the actual loaded consumers. The full-site goal stays active until its remaining matrices are closed.

## Design review closure

Spec required unified old/new arbitration, a complete producer census, protection of mounted UI and all late callbacks, usable memory-only behavior and preservation of the untouched homepage. These are explicit above; Spec returned a narrow design PASS. Standards then found that the old scope bootstrap itself could fail before reaching memory-only mode when tab storage throws. The window-shared memory tab identity, native authority check and separate get/set exception consumers close that blocker. Standards returned design and warning-copy PASS. Neither review says the ordinary failure defect is already fixed, nor substitutes for source, consumer, browser or production verification.

The later scope/attempt clarification closes a design gap found before implementation: a single v2 record could let B overwrite an inactive A failure. Standards independently approved the owner-bucket/current-candidate/CAS/read-failure contract and its extra consumer counterexamples. Narrow Spec confirmation of this addition is still pending; it does not change Marketing Batch A.

Final narrow design review closure: `/root/spec_review` read back the explicit surviving-candidate paragraph and passed the scope-bucket/CAS, active-attempt consumption and cross-bundle cold-bootstrap additions. This is design acceptance only; implementation, actual consumer and production gates remain pending. `/root/standards_review` separately passed the bucket/CAS/bootstrap design.
