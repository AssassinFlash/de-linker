# Shared product taxonomy archives: native route design

Status: design recommendation, pending an isolated local probe. This document records source analysis and the parent investigation's native readback. It does not establish an implemented repair, a successful local request, or production acceptance. Only this document was created for this assessment; no source, rewrite option, taxonomy relationship, or instance setting was changed.

## Problem and evidence boundary

The actual customer path is recorded in [chint-live-review.md](chint-live-review.md): the English Chint archive resolves as `tax-product_brand term-chint term-205`; both observed language links lead to `/de/brand/chint/`, which renders the German 404 page. The captures are discovery evidence, not version-bound final acceptance.

The parent investigation reports native readback of term 205 as `product_brand`, language `false`, and translated-taxonomy `false`; native rewrite rules contain the English `brand/...` family but no German counterpart. It also reports that `product_brand` and `pa_brand` share the `brand` rewrite base, with `product_brand` currently resolving the observed URL, and that shared `pa_series` uses `series` without German rules. These runtime facts were supplied by the parent; this design review did not rerun those reads. The raw term count and the number of displayed product families measure different things and must not be treated as an inconsistency by themselves.

The parent's subsequent isolated local native `WP_Query` read, [chint-native-shared-product-query-local.json](chint-native-shared-product-query-local.json), records the same shared term with `lang=en` returning product 2281, paired to 6720, and `lang=de` returning product 6720, paired to 2281; both titles are Chint DTSU666. This supports the existing shared-term relationship for this sample. The artifact was read for this assessment, but the query was not independently rerun here. It proves neither the missing German rewrite nor the actual archive request, switcher or template consumer.

A proper name shared by English and German is valid with `lang=false`. The failure to supply its German archive route does not justify creating a translated term or assigning a language to the shared term. The inventory's other shared terms remain candidates for individual route and consumer checks; one failed Chint switch is not proof that every shared taxonomy has the same failure.

## Native mechanism to probe

Use **`pll_filtered_taxonomies`**, which declares taxonomies whose terms remain untranslated while their associated content is filtered by language. The smallest initial candidate set is `product_brand`, `pa_brand`, and `pa_series`, subject to confirming each taxonomy's actual public product archive registration. Preserve other callbacks' entries, including the native `post_format` default. Do not turn all registered taxonomies into filtered archives.

The following native source paths establish why this is a plausible complete mechanism, rather than a route-prefix workaround:

| Native source and method | Source finding |
| --- | --- |
| `wp-content/plugins/polylang/src/Model/Taxonomies.php:78`, `get_filtered()` | Defaults to `post_format`; applies `pll_filtered_taxonomies`; intersects the result with registered taxonomies for normal reads. The hook's own documentation describes untranslated taxonomies filtered by language. |

`pll_modify_rewrite_rule` alone is insufficient: its permastruct callback must first be registered by `get_rewrite_rules_filters()`. A taxonomy absent from the translated/filtered lists can therefore be missed before a permissive `pll_modify_rewrite_rule` callback could help. Do not change the existing product/category suppression into a broad allow-all callback.

The URL-language request path must be considered as a whole. Some checks in `src/frontend/choose-lang-url.php::request()` target translated taxonomies specifically; that is not proof that a filtered taxonomy cannot work. The native filtered rule itself inserts explicit `lang`, and `PLL_Query` applies the post-language constraint. The local probe must verify the final query and result IDs, rather than infer success from one condition in `request()` or an HTTP 200.

### Early registration and the 3.8.11 static cache

`Taxonomies::get_filtered()` starts using a static taxonomy list after `after_setup_theme`. Once that list has been populated, adding the hook later does not reliably change subsequent reads in the same request. Its native documentation asks for the filter during early loading, for example `plugins_loaded`.

Register a narrow declaration from the plugin's early `register()` stage or an equivalently early hook. The declaration should add explicit names without first reducing them using a pre-registration `get_taxonomy()` result. Native `get_filtered(true)` already intersects with the current registration set; a callback that caches an empty “currently registered” subset too early can erase the intended names for the request.

The current project installs many API-dependent hooks from `pll_init`. The inspected `src/class-polylang.php` initializes its model/modules before firing that action. This is a timing risk to avoid, not a claim that every current `pll_init` execution is necessarily too late. A successful late `wp eval` filter addition is also not an adequate boot-order test. Exercise a fresh normal bootstrap with the declaration present before the first cached native lookup.

### Complete native rule family and route precedence

For the current EN/DE directory configuration with the default language hidden, the native language-prefix capture is `(de)/`. `links-directory.php::rewrite_rules()` prefixes each applicable native regex and shifts the existing `$matches[1]` through `$matches[8]` references by one before inserting `lang=$matches[1]`. It also adds the default-language query value to the original unprefixed rules in the filtered branch. This transformation retains the original taxonomy's root, pagination and feed rule shapes and their query variables.

The implementation should reuse this family. A hand-written `/de/brand/<slug>/` root rule could make one page render while leaving feed/page captures, canonical redirects, or switcher counts broken. With the existing migration active, `GermanRoutes::rules()` at priority 40 sees native `(de)/.../page/...` rules and adds `/seite/` aliases; `translation_url()` preserves the page number and `pagination()` selects the German pagination base. Probe both the native `/page/` and translated `/seite/` behavior. Their canonical response should follow the existing site policy, without an archive-identity change or redirect loop. Feed query values must retain their native meaning.

The two `brand` permastructs are an existing ambiguity. WordPress `wp-includes/class-wp-rewrite.php` applies each `{$permastructname}_rewrite_rules` filter, then merges its rules into `extra_rules_top` (`:1450`). Duplicate string regex keys can be replaced by the later merged value. This review cannot guarantee the winning registered order merely from the taxonomy names; the parent readback establishes the current Chint winner as `product_brand`.

Preserve that winner for both English and German. Record the ordered rules and matched target before/after, plus `get_queried_object()` taxonomy and term ID. Do not combine `product_brand` and `pa_brand` with an OR query, switch the winner opportunistically based on which taxonomy contains a slug, duplicate shared terms, or rename the global base to conceal the collision. A `pa_brand`-only slug under a collided base may be unreachable under the existing policy; inventory that condition and make a separate explicit routing decision if it is found. Including both taxonomy names in the native filtered list does not, by itself, prove that both identities have distinct public URLs.

### Rewrite fingerprint and activation

The current `UrlSegments::refresh()` hashes only its handcrafted German rule array. A new filtered-taxonomy declaration changes the native rule graph without necessarily changing that hash, so an unchanged option can leave the persisted rewrite cache stale.

Preferred narrow design: include an explicit shared-archive configuration/revision in the existing rewrite fingerprint, retain the soft flush after native filters are prepared (`wp_loaded` 20, after the native preparation at priority 9), and update the stored fingerprint only as the existing controlled refresh completes. An explicit one-time release soft flush with documented readback is an alternative, but the implementation must choose and test one activation contract. Do not flush every request or alter `.htaccess` for this route addition.

Test fresh-cache activation, a warm unchanged second boot, a deliberate whitelist/revision change, and rollback. Read back the persisted ordered rules and fingerprint rather than equating the call to `flush_rewrite_rules(false)` with correct routes. A rollback must restore the prior code/configuration and regenerate the matching native rules; stale new rules must not survive solely because the previous fingerprint was restored. No term migration is part of this design. Any eventual production activation still follows the project's backup and readback requirements.

Any deployed claim additionally needs release-bound readback and actual live switches.
