# Protection copy review

Scope: native staff health, the verification-only diagnostic and shared failure
messages. English is the source; German formal was written for the same states.
No product claims, access promises or automatic spam decisions are introduced.

## Draft and adversarial pass

- “Request failed” was insufficient after an uncertain side effect: it could
  encourage a duplicate inquiry. Final pending/completed-replay error asks the
  customer to check the request status before sending it again.
- “Protection enabled” overstated the shared helper's coverage. Final health
  page separates mode, key readiness and explicitly declared native handlers.
  With no consumers it states that none are connected.
- A successful diagnostic could look like a sent inquiry. The final EN/DE result
  explicitly says verification passed and no business request was submitted.
- “Total requests/cost” would misdescribe the bounded journal. Final copy says
  these are receipts within the retry window and not full traffic/exact costs.
- Vendor bodies are not customer text. All shared error messages are fixed,
  localized and omit tokens, private keys, raw inputs and upstream diagnostics.

## Final

The PHP PO/MO and native WP-CLI-generated script JSON contain the reviewed EN/DE
messages. Staff strings use Sie and do not ask the visitor to re-enter or restore
a password. The form consumer must keep the customer's fields on every refusal;
that behavior is tested in the shared client and connected in #520/#521.
Independent full-diff Spec/Standards review is recorded separately.

## Diagnostic additions after review

The initial three-column receipt counts did not explain quota refusals or reset
timing. The final surface adds current per-dimension windows and daily reason
counts, labelled with their source version. The EN and independently written DE
text explains that remaining is the minimum for an active bucket, observations
are advisory, and counters reset at UTC midnight. Native lists keep these details
readable at 390px; no new customer styles or layout channel is introduced.


## Shared verification recovery correction, 2026-10-28

Initial draft retained “Your input is still here” and described an interaction
below the status. Adversarial review found that Genie initially clears its editor
while keeping the pending question in its thread, and native forms place the
widget before the status. The draft therefore promised the wrong location and
could mislead a customer into thinking the question had already been sent.

Spec review also found that an earlier operation UUID may already have been
dispatched even when a current proof attempt fails. The first revision's “Your
message has not been sent” was too broad. The final adversarial pass settled all shared states
on the current attempt only, without making claims about an earlier outcome.

Final English and independently written German formal:

| State | EN | DE |
| --- | --- | --- |
| Checking | Checking verification. No request has been sent in this attempt. | Die Prüfung läuft. Bei diesem Versuch wurde noch keine Anfrage gesendet. |
| Interaction | No request has been sent in this attempt. Please complete the verification. | Bei diesem Versuch wurde noch keine Anfrage gesendet. Bitte schließen Sie die Prüfung ab. |
| Retry | Verification is being retried. No request has been sent in this attempt. | Die Prüfung wird wiederholt. Bei diesem Versuch wurde noch keine Anfrage gesendet. |
| Failure | Verification could not be completed. No request has been sent in this attempt. Please try again. | Die Prüfung konnte nicht abgeschlossen werden. Bei diesem Versuch wurde noch keine Anfrage gesendet. Bitte versuchen Sie es erneut. |
| Native result recovery | Checking the status of your earlier request… | Der Status Ihrer vorherigen Anfrage wird geprüft … |

Native form failure keeps the existing team-email alternative. An unknown result
from a native dispatch or unreadable ledger keeps the existing localized
status-confirmation wording. The “not sent in this attempt” sentences belong only
to proof preparation; post-dispatch timeouts retain their previous recovery rules.
The real App and Hero component regressions cover pending status, zero model
transport, and restoration of the question after verification failure.
