# 系统选型的逻辑、约束与结果是否可信？

审计日期：2026-10-22。关联研究问题：[系统选型的逻辑、约束与结果是否可信？](https://github.com/AssassinFlash/de-linker/issues/550)。本报告只研究，不修改业务实现。

## 结论与证据等级

**屋顶规划这个想法能够落实，也能够作为独立入口提供结果，再按需进入 Solution Configurator。现有实现需要重构计算与数据契约；把地图增加到 Commercial、开放欧洲地址，不能交付可相信的工商业方案。** 这个结论包含已执行的反例，不只是“也许遗漏了一些因素”。

已复现的问题包括：屋顶确定的 19 片组件在下游变成 20 片；连续跨午夜削峰需求的容量被算成物理下限的一半；CityGML 内孔被当成额外屋面；CSV 时间与数据列不校验；商业削峰输入中增加 1,000 kWp 光伏及自用目标，整个结果不变；商业硬件选择没有使用电池输出限值，并能绕过自身的多柜并联放行条件。

审计基线是 `origin/main` 的 `123aea571e80b5b1ba756816914ba86408866ba5`。根工作树的 `2b2e8267` 到该基线的六个提交，没有修改 `services/engine` 或 `plugins/linker-tools`。本报告没有把版本差当成缺陷。

证据分四种：

1. **已执行代码反例**：`probe.py` 直接导入此工作树源码，使用仓库真实商品夹具与当前发布的兼容合同；反例输入为可复跑的合成边界输入。结果在 [probe-results.json](probe-results.json)。这证明程序行为，不证明线上客户实际触发频率。
2. **适用域或设计缺口**：实际代码没有实现该计算，或所用方法的官方适用域比产品目标窄。此类不自动等同于一个已有公式的算术错误。
3. **有来源的内部数据，但本轮未重取原 PDF**：设备字段及兼容合同来自仓库现状，指出数据消费者矛盾；不冒称本轮复核了每份厂商 PDF 的当前版本。
4. **尚未验证**：生产部署同版、现场屋顶误差、真实 CSV 样本覆盖、具体并网标准现行适用条款与全欧洲精度。本轮没有访问生产写入、运行在线计算或提交询盘。

指定 Claude 审读没有完成。首次 CLI 实际路由到 `ccs-claude-deepseek--deepseek-flash[1m]`，以 `error_during_execution` 结束且无研究文本，未采用其结论；协调者尝试真实 Claude 通道时又遇到 OAuth 会话失效。本报告是可重跑计算审计及官方原文核查，不声称完成了独立 Claude 评审。执行元数据留在 `raw/claude-result.json`、`raw/claude-stderr.txt`。

## 当前真实的数据链

```text
德国邮编 + 地图点击坐标
  ├─ 州航拍影像：只作地图图层
  └─ LoD2 CityGML → 3D法向/坡度/朝向 → 2D屋面
手绘多边形 + 用户填坡度/朝向 ───────────────┘
  → 单一参考组件 + 固定边距/间隙 + 网格排布
  → 各面组件数、kWp、组件投影多边形
  → RoofStep 只向下游提交 kWp/角度/坐标/来源枚举
  → ResidentialInput
      ├─ PVGIS各屋面产量 → 月/年产量（小时序列不保留）
      ├─ HTW年用电/kWp上限 → 储能容量范围
      ├─ 逆变器规则 → 就近组串数量 → 电池兼容/数量
      ├─ HTW参考住宅查表 → 自给率、自用比例（不读当地PVGIS产量）
      └─ BOM + 屏幕报告/PDF

CommercialInput 是另一条存储定容路径：
  CSV → 最后一个数字列 → 假定每行15分钟 → 每日削峰面积 → 设备
  无CSV → 厂商经验比例 → 指示范围
  尚无屋顶、光伏时序、联合自用调度、对应设计报告。
```

证据：[`RoofStep.tsx` apply()](../../../plugins/linker-tools/src/configurator/roof/RoofStep.tsx#L444)、[`ResidentialPanel.tsx`](../../../plugins/linker-tools/src/configurator/residential/ResidentialPanel.tsx#L411)、[`models.py` ResidentialInput](../../../services/engine/src/linker_engine/models.py#L50)、[`residential.py` design()](../../../services/engine/src/linker_engine/residential.py#L777)、[`commercial.py` design()](../../../services/engine/src/linker_engine/commercial.py#L309)。

这解释了“是否绑定”：**产品入口可以独立，数学依赖不能消失。** `/roof/outline`、`/roof/pack` 的服务没有要求住宅用电量、电池或逆变器，因此屋顶几何与初步排布可以单独给结果。当前网页把入口嵌在住宅面板，保存与报告合同又没有保留完整屋顶，这属于当前结构。产量取决于排布，组串取决于实际组件，储能取决于产量与负荷，报告依赖这些结果；不宜拆成相互复制、各算一次且版本不同的工具。

## 已确认问题清单

### C1 — 屋顶片数、组串与BOM不能保持一致：实际可以增加屋顶上放不下的组件

**已执行，结果错误。** 真实商品夹具、当前兼容合同下，屋顶19片460Wp即8.74kWp，完整住宅设计选择 `GW8K-ETA-G20`，组串变为20片/9.2kWp，BOM也写20片。年产量仍使用输入的8.74kWp。另有23→24片、25→26片、29→30片、31→32片等反例；极小屋面1片会被放大为5片。

原因是 [`strings.py` _closest()](../../../services/engine/src/linker_engine/strings.py#L85) 只把目标片数当“接近值”，允许超过目标；`layout()` 没有屋顶容量约束，并且允许每面错过至多一个字符串长度。住宅候选判断检查输入kWp，组串BOM则消费调整后的片数。参考排布在手填kWp时可以建议调整，但屋顶已经确定具体位置和数量时，**调整必须回到屋顶重新放置，并重新计算产量/设备/报告**，不能隐式增片。

应锁住不变量：每面实际片数 = 可用屋顶排布中选中片数 = 组串分配片数 + 明示未接入片数；所有用到kWp的消费者来自同一组件快照。

### C2 — 跨午夜连续削峰能量可被低估约一半

**已执行，结果错误。** 7天剖面中的一个事件为20kW连续8小时，前4小时在午夜前、后4小时在午夜后，目标10kW，其余时段0kW。代码输出42.6kWh、10kW、1次事件、`short_days=0`。

事件期间没有任何充电余量，至少要向负荷交付 `8h×10kW=80kWh`；按照代码自己的94%放电效率，储能可用量下限是 `80/0.94=85.106kWh`。实际42.6kWh只可支撑约4小时。

[`commercial.py` shave()](../../../services/engine/src/linker_engine/commercial.py#L134) 在每96个样本切开日段，各段面积取最大；SOC不会在午夜物理恢复。这既不是保守误差，也不能靠“项目请人工确认”替代正确的计算。

### C3 — 充电余量判定在能量上自相矛盾

**已执行，结果错误。** 每天1h负荷20kW、1h负荷0kW、22h负荷10kW，目标10kW，重复7天。每天需从电池交付10kWh，只存在10kWh AC充电余量。代码算电池能量10.6kWh、`short_days=0`。即使充电100%无损，10kWh输入也补不回10/0.94=10.638kWh储能消耗，长期SOC必下降。

原因是 `need > room` 用未计损耗的两侧AC面积，而容量计算另除0.94；还没有充电功率上限、备电保留SOC或逐时轨迹。应统一计量边界与设备效率，并用连续SOC重放证明可行。

### C4 — CityGML内孔被当成另一片实心屋面

**已执行，几何解析错误。** 合成的合法结构由一个10m×10m外环和4m×4m内孔组成，净屋面应为84m²。当前解析返回2个屋面，面积和116m²，并给外环40片、内孔再2片。

[`citygml.py` _rings()](../../../services/engine/src/linker_engine/roof/citygml.py#L55) 抓取surface内所有 `gml:posList`，不区分 `gml:exterior` 与 `gml:interior`；`_surfaces()` 把各环直接送给 `plane_of()`。后续 `RoofPlane` 只有一个ring，无法表达孔。因此内部庭院/凹空、可表达为孔的空间，既未扣除又能被单独排组件。该合成测试不证明所有真实州数据含孔，也不证明线上某建筑触发；它证明输入一旦含孔会被错误处理。

### C5 — CSV没有时间和列语义，错误数据可得到“已定容”结果

**已执行，输入解释错误。** 672条逐小时时间戳、每条20kW的文件被读为7天15分钟数据；实际跨度为28天。再提供 `timestamp;load_kW;row_id`，解析器将行号1至672当作功率，真实20kW峰值变成672kW。所有时间戳重复也能通过。

[`parse_load_profile()`](../../../services/engine/src/linker_engine/commercial.py#L73) 选每行最后一个数字、按条数判“一周”、丢弃时间戳；没有递增性、间隔、时区、夏令时、重复/缺失、列名映射、kW/kWh识别或净购电/总负荷语义。现有负数拒绝规则是明确的，但用户真实净购电含光伏回送时，不能不经解释就当成坏数据。

重构必须先显示“识别到的列/单位/时区/时间跨度/采样率/缺失情况”供确认，再进入调度。不同分辨率不能仅改固定常量。

一周样本本身并非错误。[SMA Sunny Design官方导入说明](https://manuals.sma.de/SDesign/en-US/14318222475.html) 允许完整年或整周、明确采样间隔与功率/能量单位，并解释周数据外推；同地图外部研究者通过Apify运行 `dgJXTTKbgB6fWLT5T` 核实。这提供了成熟输入合同的复刻依据。

### C6 — Commercial没有联合光伏/自用计算，上传CSV甚至让自用目标失效

**已执行，功能缺口且接受后不消费输入。** 同一削峰CSV与目标峰值，增加 `goals=[peak_shaving,self_consumption]`、`pv_kwp=1000` 后，返回对象逐字段完全相同，且仍为 `status=sized`。若只有self_consumption目标并上传CSV，只给削峰选项，不计算光伏自用方案。

[`commercial.py` CSV分支](../../../services/engine/src/linker_engine/commercial.py#L333) 提前return；后面的pv_kwp经验比例只在无CSV分支执行。CommercialInput也没有屋面、地点坐标或PV序列字段。不能对用户把这个结果称为“厂房屋顶+光伏+储能联合优化”。

这是尚未建设的能力。使它可行，需要当地阵列产量时序与用户负荷先在时间上对齐，明确现有光伏在负荷计量中是否已经扣除；再定义自用/削峰/备电目标及调度优先级。否则有双重扣减光伏、只改储能指标的风险。

成熟范例可参照 [SMA Sunny Design多目标电池使用](https://manuals.sma.de/SDesign/en-US/14444632075.html)：其multiuse按SOC区间协调削峰与自用；同地图外部研究者通过上述Apify运行获取原文。该范例支持建立统一SOC模型，不支持把两个经验容量简单相加后宣称联合最优。

### C7 — Commercial系统功率只取逆变器铭牌，不受电池功率约束

**实际数据消费者矛盾已复现；厂商PDF本轮未重取。** 输入75kW、60kWh，`commercial.systems()` 首推 `GW80K-ET-G10 + GW61.4-BAT-AC-G10` 并显示80kW系统功率。当前兼容合同对这组设备的条件明确说不能达到逆变器满功率；仓库商品夹具的电池 `max_charge_discharge_power_kw` 为55.2/67.5kW，出处指向托管BAT-C数据手册第2页。

[`systems()`](../../../services/engine/src/linker_engine/commercial.py#L208) 筛选只核容量及兼容枚举，`power_kw` 始终是逆变器AC功率×台数；不读取电池电流/电压/功率、SOC、温度及PCS电池输入限制。**有兼容放行，不等于能达到所需连续输出。** 应以该组合在验证条件内的可交付功率决定是否满足削峰与备电，不把文字条件留给用户自行发现。

### C8 — 按容量增配一体柜后可以绕过并联放行门

**已执行，程序约束漏检。** 当前兼容合同中 `GW125/261-ESA-LCN-G10` 没有parallel_controller条目。`systems(100kW,600kWh)` 仍返回3柜、375kW、783.8kWh，未附并联放行或控制器依据。

[`commercial.py` L180–192](../../../services/engine/src/linker_engine/commercial.py#L180) 先按功率得到1柜，检查多柜限制；随后为了容量变为3柜，只检查“存在max_units时是否超出”，没有在缺少max_units时重新拒绝多柜。这并不能证明实物禁止并联，而是证明代码违反自己的“没有文档不推多柜”约束。

### C9 — 当地产量与自给率各算各的，参考表不能支撑全欧洲/商用精度

**已执行的数据流边界；不把HTW原表本身判为错误。** 同一5.52kWp、4,000kWh/a家庭与电池，把注入的产量来源从400改成1,400kWh/kWp：完整设计年产量2,208→7,728kWh，自给率/自用率对象逐字段不变。低产量合成夹具下自给率仍为61.84%–71.84%，但即使所有太阳能都无损给负荷，物理上限也只有2,208/4,000=55.2%。这证明把两个各自有出处的结果拼在一起，也可能产生互相违反能量上限的项目结果；不是对一个真实地点做了此次PVGIS实测。

这是因为 [`htw.metrics()`](../../../services/engine/src/linker_engine/htw.py#L129) 只读总kWp/年用电/容量，[住宅调用](../../../services/engine/src/linker_engine/residential.py#L913) 没传产量；输出是HTW参考家庭的查表值。代码确实会在热泵、EV或年用电越域时显示rough guide警告，因此不能说它完全没有警示；但**警告没有使该数字成为当地项目的模拟结果**。

[HTW官方FAQ](https://solar.htw-berlin.de/faq-unabhaengigkeitsrechner/) 说明其气象、南向35°、无热泵/EV、特定住宅负荷假设，并明确建议热泵/EV使用其其他工具；重抓原文在 [raw/06-…htw-berlin.md](raw/06-faq-zum-unabh-ngig-keitsrechner-htw-berlin.md)。定位或屋面变了，自用/自给率不变的模型不能直接升级为欧洲工商业“设计准确度”。

HTW的住宅定容上限可以保留为有出处的参考对照；真实联合计算应另有PV与负荷时序、设备和SOC模型，再明确验证域。现有±5个百分点源于特定住宅研究，不应当成所有国家/朝向/工商业的保证误差。

### C10 — 平屋顶结果目前只是单一几何排布，不能据此承诺工商业安装量

**设计缺口/适用边界；并非所有平屋顶片数一定错。** 低于10°时，packing把坡度当0、网格朝南；没有组件安装倾角、单排南向/东西向双排、支架型号、行间遮挡距离、过道、天窗、烟囱、女儿墙、屋面承重、风雪区域或消防分区输入。只有固定2cm夹缝及0.3m所有边内缩，没有平屋顶安装几何模型。

如果明确假设贴屋面、无障碍、只做几何容量，这类初算有意义。但现在字段没有区分**建筑屋面坡度**与**组件安装坡度/朝向**；10°以下朝向被packing覆盖，传PVGIS的却仍是原屋面角度。是否安全可装、哪种架台最好、行距应多少，不能从同一个默认数猜出。

新增工商业时应引入有厂商依据的安装类型与约束，保留可编辑障碍/禁布区，并在数据不够时给明确的几何上限或待确认结果。自动识别精度、设计精度和安装审批是三个不同层级；具体能力由证据支撑后再命名，不能靠免责声明模糊。

### C11 — 报告没有保存屋顶计算足迹，重开后无法证明原始屋顶结果

**合同缺口已由源码及生成报告确认。** RoofSelection回传kWp/数量/每面角度/坐标/粗来源枚举，ResidentialInput丢失屋顶多边形、组件位置、模块明确型号/版本、排除区、LoD2建筑/面ID、影像日期与混合来源。当前来源枚举只有drawn或lod2，一面官方就把混合结果概括为lod2。

[`report.py` NOT_REPORTED](../../../services/engine/src/linker_engine/report.py#L21) 明确把屋顶五个未核实假设排除于最终报告，理由是它们在屋顶步骤另行显示；[最终assumptions](../../../services/engine/src/linker_engine/report.py#L355) 无法补回。PDF有产量来源与设备文档，有实际规则说明，不能说“全无依据”；但**不能从保存的报告重建当时画了哪片屋面、减了什么、用了哪些布局假设**。

独立入口必须把完整RoofDesign快照保存下来，报告与Configurator都引用它，版本改变要使下游结果失效或重新计算。

### C12 — 备电和标准判断有实质适用边界，不能把容量通过当成整套设计通过

**已执行当前设计选择，未验证逐设备备电能力。** 住宅代码刻意把备电当容量输入，`backup_storage`只检容量。输入关键负荷10kW、30分钟，得到5.32kWh备电预留；完整设计仍选择 `GW5K-ETA-G20`，其夹具备电额定值是5kVA，所有已有资格规则通过。这个输出只能证明容量储备，不能证明它能承受输入的10kW关键负荷。缺少逐设备可核验的EPS连续功率、峰值时长、切换/隔离、相数、不平衡与电池限流判断。商业也把reserve加能量，但削峰路径功率仍按削峰差值计算，没有把关键备电负荷并入设备功率需求。

这在当前规格及后续代码记录中是明确行为，不能冒称是遗漏了一个已经承诺的字段；但当客户选择“备电”并得到完整产品建议时，产品必须说明验证到哪层，并让设备能力约束参与选择。重构应把**容量储备**与**备电供电能力**分开验证。

同时，Commercial把 `grid_connection_kva` 与名为135kW的常量比较，另有按服务容量触发发电设备保护提示的逻辑，单位及适用对象未区分。德国阈值不能随国家开放继续通用；现行标准原文与国家/DSO规则本轮未全核，不对具体国家作合规通过结论。

### C13 — 必要配件缺失时仍给放行系统，BOM静默少件

**故障注入已执行，明确的闭环缺陷。** 在商品夹具中移除 `BC2-HV1`，不修改当前兼容合同。指定 `H2-10K-T3 + BU2-5.0-HV1` 后，住宅设计依旧选中，放行类型仍是 `released_with_accessory`，条件正文仍说明必须BC2；BOM只有H2和BU2，缺少BC2。

[`_battery_lines()`](../../../services/engine/src/linker_engine/residential.py#L464)、[`_requirement_lines()`](../../../services/engine/src/linker_engine/residential.py#L487) 和商业附件循环在匹配不到商品时直接continue，没有把完整系统设为未完成，也没有给安装商范围的明确必需行。这不证明今天线上BC2缺失；它证明配件被下架、feed没同步或规则正则不再匹配时，选型仍会被包装成完整方案。必要附件应是资格/完整度约束，不能仅是尽力输出的BOM装饰。

### C14 — 电池电气约束字段与堆叠配置之间没有可执行连接

**故障注入已执行，证实缺少数据消费；不是宣称某真实配对必然电压不兼容。** 把BU2电池字段改成2000–2500V和最大放电电流0.01A，保留配对合同和数量数据，`stacking.configurations()` 的可选数量与kWh列表完全不变。源码中的 `battery_voltage_range_v`、`operating_voltage_range_v` 目前只定义解析器，没有被定容或选型消费。

单纯比较两个电压范围也不足以修复：某些设备存在DC/DC，数据可能是电芯侧、堆叠总压或逆变器端口，范围必须先有语义。当前的数量选择仅靠枚举放行和模块范围，不能自动证明每种堆叠的有效电压区间、BMS/PCS限流、最低启动点、热降额与实际功率。

应建立带端口与工作条件的电气配置事实，能够从实际电池堆叠计算/引用可工作窗口，再给出这个组合的可交付功率与适用SOC。资料不足的配置必须显式标出缺什么，不能从一个系列级放行枚举推出每一种数量均有效。

## 系统选型方法的逐层信任清单

用户要求核查“系统选型逻辑本身是否错”。因此以下逐层区分三类：**A：已独立核算，可在注明范围内复用；B：已证实错误/不能保真，必须替换或重构；C：目前只有规则声明、经验偏好或部分数据，尚不能认定任务级正确。** A只代表该小模块，不代表系统整体通过。

| 方法/约束 | 当前行为和消费者 | 结论与证据 |
|---|---|---|
| 数值单位换算 | W→kW、Wh→kWh按单位；不识别的单位为None | **A（局部）**：独立断言10000W=10kW、5000Wh=5kWh、未知单位不猜。kVA与kW仍需类型隔离，不能沿用一个float暗示相等 |
| 数据引用与语义 | feed Schema要求URL/字段结构；`units.number()`读文本第一数字，复合安装条件/上下限仍可丢语义 | **C**：有引用不等于引用页真正支持字段，也不等于条件被执行；需要逐字段来源/端口/单位/适用条件核实 |
| 住宅用途/相数 | home且相数相等；相数未知不通过；既有逆变器只查相数与后续电池 | **A（门逻辑）/C（产品事实）**：未知保持未知已验证；用途来自厂商标注而非物理定律；既有机路径不是完整PV复核 |
| 单相限制与并网 | 以AC kW对照4.6kVA；30/135阈值驱动提示 | **C**：不能将活跃功率、视在功率、服务连接容量及发电容量混为一项；全欧洲必须按国家/DSO及项目类型核实原文 |
| PV输入上限与DC/AC | `pv_input_kw≥输入kWp`；另一DC/AC判断实为同一上限除AC功率 | **A（不超过已给上限的比较）/C（完整设计）**：比较本身明确；两个绿勾不是两个独立物理证明；并没有按气候产量、削顶、MPPT各面实际功率优化 |
| 组串整数分配 | 各面留独立MPPT，以最接近目标总片数选字符串长度和并联数 | **B**：C1已证屋顶片数被改变；同朝向是否能合并、异向接法及未接入片数需要完整合同，当前plane关联在响应StringGroup中又丢失 |
| 组串电压温度 | Voc冷态按-10℃；热Vmp使用Voc温度系数；最大MPP电压使用STC Vmp | **C**：这是一组有声明的近似，不是逐地点极端温度/逐模块Vmpp参数验证；不具全欧洲气候通用证明 |
| MPPT电流/熔丝 | 用Impp/Isc限每MPPT并联数；熔丝按每MPPT分组反灌公式 | **A（隔离分组算术可复用）/C（标准/设备条件）**：现有真实夹具反灌案例测试通过；标准版本、设备内部拓扑/保护、双面增益/温度和组件选择变更后仍需独立基准，不能声称所有安装合规 |
| 配对枚举 | 未知不放行；多条匹配取更严格结论、模块范围交集 | **A（组合机制）/C（内容）**：未知与窄拒绝覆盖宽放行的独立控制通过；条件文字没有变成电气/固件/应用条件的可执行约束 |
| 堆叠数量/总容量 | 模块min/max、并联stack数量及部分系统cap → 数量×usable_kWh | **C**：保留数量枚举机制的价值；未验证所有电池的模块/成套单位语义、不同安装方式和端口电压；C14证明电气字段改变不影响配置 |
| 住宅定容上限 | HTW三个规则，预留另加；无热泵/EV时low=high，实际是上限不是推荐区间 | **A（规则复现）/C（推荐值）**：10kWp/4000kWh→最多6kWh已独立算术验证；这不证明默认6kWh最佳，也不证明更小电池无效 |
| 住宅电池默认选择 | 每个电池取上限内最大配置；都超过时取最小并警示；备电仅过滤容量不够 | **C**：这是项目自己的离散偏好，不是HTW推荐模型；未用边际自用收益、损耗、实际电池功率、价格或客户目标比较 |
| 住宅整套排名 | 先使 `abs(AC_kW-PV_kWp)` 最小（0.1kW取整），再电池是否超上限/容量、配件、件数、产品ID | **C**：稳定排序可以复用；“AC最接近PV”和“电池靠近上限”没有被证明是最优工程目标。排序不能弥补资格约束缺失 |
| 备电容量与设备 | P×h/0.94容量预留；没有EPS功率/切换约束 | **B（若声称满足备电任务）/C（明确只算预留时）**：C12的10kW需求仍选5kVA设备，规则全通过；这是现规格刻意范围，重构必须改变任务合同 |
| 光伏与负荷/储能时序 | 住宅PVGIS年/月汇总，与HTW百分比独立；商业CSV不消费PV和自用目标 | **B（作为联合设计能力）**：C6/C9可重跑；不是只加一个地图调用即可完成 |
| 工商业削峰SOC/补能 | 每天最大超峰面积/0.94；用每日room检查 | **B**：C2/C3违反连续能量与补能条件，必须替换计算；不能保留公式再加警示 |
| 工商业设备功率 | 以逆变器AC铭牌×台数为系统功率；电池只用kWh达标 | **B**：C7硬件数据矛盾，功率链未验证；实际调度必须用组合可交付功率 |
| 并联台数 | 初始功率决定台数，按容量增柜再漏查缺失放行 | **B**：C8无需依赖外部解释即可证明程序违反自己约束；所有变更必须重验 |
| 附件/电表/BOM | 读取合同并按system/stack等数量输出；匹配不到产品则跳过 | **B（闭环完整性）/C（逐件数量语义）**：C13故障注入可重跑；部分当前电表已明确随箱，不能因审计再重复加购；必须逐件证据化 |
| 工商业排名与现场 | 先最小总功率、再容量、再ID，取3组；site输入不参与设备过滤 | **C**：现行最小设备排序不是多目标最优方案；安装室内/外、并网允许量及服务条件未进入可执行资格 |
| 报告/保存/UI消费 | 复用Report模型，展示已通过规则；BOM消费组串，产量消费输入，屋顶足迹丢失 | **B（同一项目一致性）/A（同Report渲染基础）**：C1/C11；源码存在的conditions不等于主卡片解释或选型已应用条件，需逐消费者验收 |

主要依据是 [`residential.py` evaluate/battery_options/system_key](../../../services/engine/src/linker_engine/residential.py#L143)、[`stacking.py`](../../../services/engine/src/linker_engine/stacking.py#L37)、[`compatibility.py`](../../../services/engine/src/linker_engine/compatibility.py#L122)、[`eligibility.py`](../../../services/engine/src/linker_engine/eligibility.py#L31)、[`products.py`](../../../services/engine/src/linker_engine/products.py#L157)、[`units.py`](../../../services/engine/src/linker_engine/units.py#L28) 与探针新增控制/故障注入。

**因此不能把旧规格当成正确性证明。** 旧规格确实规定HTW查表、AC接近PV、容量优先等范围，后来又刻意把备电从硬件能力门改成容量门；这些能解释实现为何如此，却不能证明“客户据此选出的系统会完成其任务”。本轮允许推翻架构，应按任务验收重新定义输入、硬约束、目标、方法、证据和退出条件。

## 哪些部分已有可用基础

- 使用投影米做排布、WGS84用于地图，整体坐标/单位分层合理。独立30°平面算例得到面积100m²、倾角30°、朝向180°，与解析几何一致；没有证据说整套面积/投影都错。
- 源数据缺失时，部分逆变器会因engineering_data未知而不进入住宅建议；兼容合同不把无记录配对当作放行。应保留这种证据不足即不宣称通过的设计。
- HTW三条初筛上限有可追出处；PVGIS确实被执行来算产量，非仅在注释里挂名。屏幕与PDF共用一个Report模型，设备手册链接与部分规则数值已经进入报告。
- 无CSV的商业路径确有indicative状态、短样本警示及询盘出口，不是所有商业输出都自称精确。

现有27项屋顶/组串/HTW/工商业测试全部通过，而本轮反例仍成立。这说明这些测试没有覆盖上述不变量，不能用现有绿灯证明工程结果正确。

## 可行的重构边界与不可违反的不变量

建议把它重构为一个共享项目模型下的几个可独立验证模块。屋顶工具可单独成为网站重点入口；客户在没有用电账单时也应获得有明确含义、可保存的屋顶结果，再选择是否继续算发电/整套方案。独立入口不要求复制后端引擎。

| 模块 | 负责的事实与结果 | 必须证明的不变量 |
|---|---|---|
| Project/Site | 国家、位置、时区、数据源版本、负荷计量边界 | 国家和位置决定规则及气象；负荷是总负荷/净购电/含既有PV必须明确 |
| RoofGeometry | 外环/孔/障碍、坡度/朝向、屋面与数据置信信息 | 面积/孔守恒；无重叠假面；几何可重放；来源逐面保留 |
| ArrayLayout | 组件型号、安装方式、支架倾角/方位、排布和禁布区 | 组件不越界、不重叠、不落孔；片数精确等于图上模块；行距与边距有适用条件 |
| YieldModel | 逐阵列气象产量、模型/损耗/地平线/遮挡假设、采样语义 | 同一快照片数与kWp；总产量=各阵列产量和；小时来源不伪装成实测15分钟精度 |
| LoadProfile | 列映射、单位、时区/夏令时、完整度、代表性 | 时间有序、间隔明确、缺失有策略；输入能源边界不混淆；原始文件hash可追溯 |
| StorageDispatch | 连续SOC、充放电/损耗、备电保留、削峰/自用优先级 | 不跨午夜重置；功率/容量/SOC上下界始终满足；能量守恒；不可行目标显性返回 |
| DeviceSelection | 逆变器、实际电池配置、并联、兼容附件 | 所有数量变更重新验证；可交付功率受链路最弱约束；组串不能隐式改变屋顶 |
| Evidence/Report | 单个已计算项目版本与来源清单、条件、未核实项 | 图、BOM、产量、设备、PDF同版本；旧结果更新/失效明确；不能只留来源名称 |

可信度不宜靠一个笼统“精确”徽章表达。应逐结果列出：来自数据源的事实、客户确认输入、计算出的值、假设、待核项，并给可展开的方法与直接来源。若某输入尚不够，保留已经算得出的屋顶/产量结果，同时明确哪一段方案还不能下结论。

实施前建议先确定两个输出合同：

1. **独立屋顶结果**：可用屋面、已确认/未确认障碍、某组件和安装方式的初步排布、片数/kWp、数据与假设、可保存的图及来源。是否加入产量由数据可用性决定，不能强迫客户先填住宅年用电。
2. **继续系统方案**：选择住宅/工商业需求、补负荷或粗筛资料，引用该屋顶快照进入发电/储能/设备/报告；实际时序资料不足时，输出已验证的部分和需团队核实的部分。

工商业联合计算在技术上有成熟建模路线；真正的成本在输入语义、安装规则、设备功率数据、时序精度与验证样本。欧洲地址能统一，自动屋顶和规则不能保证各国同等覆盖。**不应在现有错误链上扩大使用承诺；应先建立统一项目与结果契约、计算不变量和独立基准算例，再改用户流程及可发现性。**
