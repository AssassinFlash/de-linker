# Embedding bake-off：模型、检索形态与索引位置（票 #10）

日期：2026-10-10（构建与评测都在本机 Mac，Apple M3 Pro）。规格：`docs/specs/10-knowledge-index.md` §模型对比。
数字来源标注：**实测** = 本次 bake-off 我方测得（原始 JSON：`~/de-linker-data/index/bakeoff-20261010.json`，语料与索引构建清单在各 build 的 `manifest.json`）；**估** = 按 `embedding-models.md` §2.3 的 FLOPs 方法推算；**前测** = 上一执行线在 VPS 上的实测，载体是代码注释（`index/local_model.py` docstring），本次未复测。

## 0. 结论

1. **模型：`gemini-embedding-2`（AIHubMix API，3072 维）胜出。** 相对最强开源对照（BGE-M3），召回@5 高 **13.0 个百分点**（56.9% 对 43.9%），页码正确率持平（83.0% 对 82.9%）。决策规则（API 提升两项都 <5pp 才用开源）不成立 → **用 API**。
2. **索引位置：A。** 块与向量进共享主机的 MariaDB（VECTOR 列 + 向量索引 + FULLTEXT），`search-knowledge` 成为 linker-commerce 里的纯 PHP + SQL，查询向量经 API 取得；VPS 只保留 Genie 代理循环。构建管线不变（Mac 离线），`index.mariadb` 已产出 `index-mariadb.sql`。
3. **C 检验（纯 BM25 与混合的差距）**：BM25 单独 28.8%，BM25+gemini 45.3%，**差 16.5pp ≥ 5pp → 不取消向量**（单列表见 §3）。
4. **多模态否决**：gemini 页面向量（11,697 页 PNG 经 Gemini 原生 `embedContent`）在图类子集 47.0%，低于同一模型纯文本块检索的 60.6%，全量也更低——页面图像检索不进产品，与 `embedding-models.md` §3.3 的判断一致。Apple Vision OCR 页文本向量（arctic）在图类子集 37.9%，也不敌同模型块检索的 40.9%。
5. **检索形态变更：向量排名独立成序，不再与 BM25 做 RRF 融合。** 等权 RRF 让胜出模型损失 11.6pp 召回@5 与 3.2pp 页码正确率（45.3%/79.8% 对 56.9%/83.0%）；加权 RRF（2:1、3:1）实测更差。BM25 降为本机没有该索引模型的查询编码器时的回退（规格原有的回退路径不变）。
6. **验收阈值未达，差距与原因见 §5**：最优配置召回@5 56.9%（阈值 90%）、页码正确率 83.0%（阈值 95%）。诊断链证明这不是实现缺陷：黄金数据本身健全（91% 的问题其逐字引文就在金页上）、暴力检索上限、候选池上限都远低于 90%，原因是黄金集把"卡片作者读的那一页"定为唯一正确页，而同参数行在数十页同构参数表里反复出现。

读法：
- 跨语言是向量的决定性贡献：BM25 在德问英档上崩到 14.5%，gemini dense 53.8%（研究预判，`embedding-models.md` §2.2 结论 3，本次实测一致）。
- 开源里 BGE-M3 略高于 arctic（43.9% 对 41.0%），但 BGE-M3 不能上 VPS（§4），arctic 是开源侧的实际首选。
- 所有 RRF 融合都低于其 dense 单路——本语料里"别的型号的参数表"与查询词的词面重合度太高，BM25 注入的是噪声排名。加权 RRF 实测（gemini）：等权 46.6%、2:1 35.8%、3:1 36.1%、纯 dense 56.9%，确认独立向量序最优。

## 4. 延迟、内存与成本

查询延迟（每问一次编码，p50/p95；**实测**，本机）：

| 模型 | Mac 单线程 p50/p95（实测） | VPS 1 vCPU（估，§2.3 方法） | 备注 |
|---|---|---|---|
| arctic-embed-m int8 ONNX | 51.5 / 105.0 ms | 40–80 ms | 估按 §2.3 为 20–40 ms；Mac 单核更快，取两者区间并注明 |
| e5-small int8 ONNX | 7.9 / 34.8 ms | 5–15 ms | 同上（§2.3 估 5–10 ms） |
| BGE-M3 | 54.7 ms（MPS，**不代表 VPS**） | fp32 p95 254 ms、RSS 1.5 GB（**前测**，代码注释） | fp32 权重 2.27 GB 超 VPS 预算（引擎+Genie+模型 ≤3 GB 无 swap）→ B 方案下不可用 |
| gemini-embedding-2（API） | 1905 / 2404 ms | 网络往返同量级（共享主机出口未测） | 查询 token 约 30/问 |

内存（VPS 预算，**估**，`embedding-models.md` §6.2）：arctic int8 会话+模型 350–450 MB；e5-small 150–200 MB；BGE-M3 fp32 1.5 GB（前测）超限。A 方案下 VPS 不跑任何模型，此项仅约束备选 B。

成本（**实测**计数 × 公开单价）：
- gemini 语料嵌入：抽样 200 块 = 60,353 token（302 token/块）→ 全语料 32,852 块 ≈ **9.91M token**；AIHubMix 单价文本输入 $0.45/M（aihubmix.com/model/gemini-embedding-2，2026-10-10）→ **重建一次 ≈ $4.46**。
- 查询：~30 token/问 → 1 万问/月 ≈ 0.3M token ≈ **$0.14/月**。
- 多模态页向量（已建，被否决）：11,697 页 3,017,826 token，图像单价 $12/M → $36.21 一次性（沉没成本，不进产品）。
- 开源模型：$0。

索引体积（SQLite，**实测**）：关键词 49.1 MB；e5-small 384 维 101.8 MB；arctic 768 维 153.8 MB；BGE-M3 1024 维 188.4 MB；gemini 3072 维 465.5 MB。A 方案将这些搬进 MariaDB（`index-mariadb.sql`，含 FULLTEXT + VECTOR(3072) + 向量索引）。

## 5. 验收阈值差距与原因（不达标的证据链）

票面阈值：召回@5 ≥ 90%、页码正确率 ≥ 95%。最优出厂配置（gemini dense、by-product、页级）：**56.9% / 83.0%**。差距 33.1pp / 12.0pp。这不是实现缺陷，证据链如下（全部**实测**）：

1. **黄金数据健全**：EN 492 问中 448 问（91.1%）的逐字引文能在索引内金页文本中找到——数据没问题，是检索排序把金页排得深。
2. **暴力检索上限**（不圈定、不限候选、按页折算）：arctic @5 35.1%、@50 75.7%、前 200 页仍找不到 7.5%；gemini @5 45.3%、@50 79.6%、找不到 5.5%。任何模型的一阶段排序都到不了 90%@5。
3. **候选池上限**：出厂混合（BM25+dense 各 top-30，RRF）在 @50 的召回 73.5%——即使接一个完美重排器，73.5% 就是池子上限，仍 <90%。
4. **排序困难的结构原因**：黄金集把"事实卡作者读过的那页"定为唯一正确页，而同一参数行（"Max. AC Output Current 198.5"）在数据表、家族手册参数章、宣传册里逐字重复；型号码又出现在几十份兼容表里。逐案检查（如 "maximum AC output current of GW125/261-ESA-LCN-G10"）：金块在 BM25 全量排名第 14/56 位，前 5 全是其它型号的同类参数表——每个信号（词面、语义）都"正确地"偏向同构页。
5. **修正口径也不够**：把命中放宽为"前 5 页任意一页携带黄金引文"（答案可引用的页即算对），出厂配置 57.3%——不是口径问题。

可选的后续方向（超出本票，归 #13 决策）：两阶段检索——粗排取 top-100~200 页（暴力上限 94.5%）、再用跨编码器（bge-reranker-v2-m3）或 API 重排进前 5。VPS/共享主机跑不动本地重排器（568M 参数），API 重排需另立供应商评估。黄金集口径也可复议：以"携带引文的页"为命中（57.3%）或按 recall@10（68.2%）设阈，需要协调线裁定；本报告只给数字。

## 6. 决策依据归档

- 决策规则（规格 §模型对比）：API 相对开源在召回@5 与页码正确率的提升都 <5pp → 开源；否则 API 并记月成本。实测：gemini 对 BGE-M3 召回@5 +13.0pp（≥5）→ **API**；月成本 $0.14（§4）。
- 位置 A 的含义（规格"索引放在哪里"）：块与向量进 WordPress 的 MariaDB（`wp_genie_*`，`index-mariadb.py` 生成），`search-knowledge` 是 linker-commerce 的纯 PHP + SQL（FULLTEXT + `VEC_DISTANCE_COSINE`），查询向量经 API；VPS 不跑模型。BGE-M3 因内存出局使 B 方案只剩 arctic（41.0%），进一步支持 A。
- 出厂检索形态：`linker_genie/retrieval.py` 向量独立成序、BM25 为无编码器时的回退（§2 表与加权实验为据）。
- 黄金集与评测工具：`services/genie/index/eval/`（goldset/bakeoff/run），`just eval` 对最新索引打分并按票面阈值判 FAIL（本次 FAIL 即 §5 的记录）。
