## Contract for the managed fetch

The following separates provider facts from the proposed application policy.

1. **Start and retain identity.** Server code fixes the Actor and exact numeric build, constructs only the approved PVGIS endpoint/query from validated coordinates and declared database/year/horizon policy, and owns the complete Actor input. Do not accept customer Actor IDs, URLs, proxy/header/hook/page-function settings or webhook destinations. For one weather response, explicitly set Cheerio, depth 0, page/result counts 1, concurrency 1, bounded request timeout/retries and `saveContentTypes=application/json`; retain submitted and effective INPUT. The pinned Actor's schema documents depth 0 as start-URLs only and exposes independent crawl/result/request limits. Its `maxResults` may count downloaded files; do not infer a strict single-record response from those limits. [Pinned build schema selection](raw/apify-metadata.json), [actual working weather input](../2026-10-24-pv-generation/raw/acquisition-input.json).
2. **Bound asynchronous execution.** POST returns a run object, not fetched weather. `waitForFinish` defaults to 0 and is capped at 60 seconds on both start and GET run. Use `GET /v2/actor-runs/{runId}` with a per-request bound and a separate overall deadline/cancellation check; do not poll indefinitely. Official statuses are `READY`, `RUNNING`, `TIMING-OUT`, `ABORTING` (nonterminal) and `SUCCEEDED`, `FAILED`, `TIMED-OUT`, `ABORTED` (terminal). Preserve the hyphens. Only successful completion may proceed to body validation; other terminal outcomes fail visibly. Early final stats/costs may still change; the GET docs advise a later read for stable accounting. [Run Actor](https://docs.apify.com/api/v2/act-runs-post), [Get run](https://docs.apify.com/api/v2/actor-run-get), [lifecycle](https://docs.apify.com/platform/actors/running/runs-and-builds).
3. **Resource limits are distinct.** Run query parameters provide timeout, memory, restart-on-error and optional total-charge cap. Memory is a power of two, at least 128 MB. `maxItems` is a pay-per-result billing cap and explicitly does **not** guarantee returned item count. Application deadlines, decoded-body/row bounds, retry/backoff counts and cost budgets are deployment policy to choose explicitly, not provider accuracy guarantees. Our 180-second/1024-MB settings are acquisition evidence, not a production sizing recommendation. [Run parameters](https://docs.apify.com/api/v2/act-runs-post).
4. **Read the admitted dataset only.** `GET /v2/datasets/{defaultDatasetId}/items?format=json&offset=0&limit=...` supplies records. The API has no default item limit; pagination and a response-byte bound must be explicit. `clean=true` also skips empty and hidden items, so it is a presentation filter, not an integrity check. Preserve the original nested shape. Validate the exact expected URL/query, `crawl.loadedUrl`, `crawl.httpStatusCode`, `crawl.contentType`, and the unique matching `fileUrl`; reject missing/duplicate/foreign records. The working weather capture has `application/json`, status 200, and a file record, while `text`, `markdown` and `html` are null. Those extracted text fields are not raw weather. [Dataset API](https://docs.apify.com/api/v2/dataset-items-get), [actual weather record](../2026-10-24-pv-generation/raw/acquisition-items.json).
5. **Download and validate raw bytes.** Resolve only an admitted record belonging to that run's `defaultKeyValueStoreId`, using `GET /v2/key-value-stores/{storeId}/records/{recordKey}` and server-held Bearer authorization. Do not follow an arbitrary dataset URL or carry authorization to an unexpected origin. Strip temporary signature queries from persisted evidence; authenticate privately. The API returns the stored record with its content type and can decompress content; it also documents 302 responses. Reject unexpected redirects unless an explicit trusted redirect policy is implemented. Apply the decoded-byte bound while reading, then verify media type, strict JSON/schema, full input echoes, coordinates/database/years/horizon, source units/time policy and resource bounds before publishing a project asset. Record raw SHA256, provider capture and transformations. [KV API](https://docs.apify.com/api/v2/key-value-store-record-get), [downloaded originals](raw/files-provenance.json), [existing weather provenance](../2026-10-24-pv-generation/raw/weather-provenance.json). `crawl.contentLengthBytes` is not a decoded-byte equality assertion: the source-file capture reports 14520 while its downloaded body is 60724 bytes and matches the pinned source hash.
6. **Cancellation and ambiguous start are separate states.** `POST /v2/actor-runs/{runId}/abort` aborts an active run; default is immediate, while `gracefully=true` allows 30 seconds for persistence before force-stop. Check the returned/read-back state, and independently prevent any cancelled local operation from publishing a late result. No abort was executed for this research. [Abort endpoint](https://docs.apify.com/api/v2/actor-run-abort-post), [lifecycle](https://docs.apify.com/platform/actors/running/runs-and-builds). The start endpoint documents no idempotency-key parameter or duplicate-start guarantee. Treat a lost POST acknowledgement as **unknown whether a run was created**, not permission to repeat the POST automatically. Persist a local intent and acknowledged run ID, reuse that run for retries, and expose ambiguous-start recovery explicitly. This last policy is an engineering inference from the documented interface, not an Apify exactly-once promise.

An important observed failure mode: this run's status message says “6 succeeded, 2 failed”, yet the two failures are Cheerio's download-handoff `navigation: Download is starting.` events. The separate FileDownload phase then reports 2 finished/0 failed; both KV downloads are HTTP 200 and valid originals. Therefore the summary string/failure count alone cannot attest or invalidate a file asset. Require successful run identity **and** the matching capture **and** valid retained bytes. [Compact log evidence](raw/docs-log-selection.json), [file download provenance](raw/files-provenance.json). ## Exact module coefficient

The existing engineering overlay already cites the hosted **Trina TSM-460NEG9R.28** English datasheet. The original was reacquired through the pinned Actor because no retained original of this exact PDF was found in the repository. Page **2**, version **TSM_EN_2024_C**, lists the 460-Wp variant and Pmax temperature coefficient **−0.29 %/°C**. Thus the pvlib/PVWatts fractional coefficient is **−0.0029 per °C**, obtained by dividing the percentage by 100. It is not −0.004 and must not be substituted by another brand's generic value. Page 2 also lists front and back glass, confirming glass/glass construction. [Hosted manufacturer datasheet, page 2](https://de-linker.com/wp-content/uploads/2026/09/240831_Datasheet_Vertex-S_NEG9R.28_EN_2024_C_web.pdf#page=2), [exact retained PDF](raw/trina-neg9r28-en-2024c.pdf), [verified extraction and arithmetic](raw/model-input-verification.json).

PDF: **488969 bytes**, SHA256 `f4d280f9a0d89475cf575fbb99906e2b091da27f08b848fc51877cc1d24e8e22`. Retain the source model/page/unit with the selected coefficient. This confirms one reference module's declared rating, not the installed module or a system release.

## SAPM scenarios pinned to pvlib 0.16.1

The tagged upstream `pvlib/temperature.py` was downloaded through the same Actor. Its SHA256 is `2adbab834d25836007bad5fc429acd2b53b83dc99b7be6d288bc1644d5a18319` (60724 bytes), identical to both the earlier tag/tree verification and installed source. Lines 15–21 define these named sets; the function documentation describes their construction and ventilation basis. [Tagged primary source](https://github.com/pvlib/pvlib-python/blob/v0.16.1/pvlib/temperature.py#L15-L21), [retained original](raw/pvlib-0.16.1-temperature.py), [earlier tag verification](../2026-10-24-pv-generation/raw/pvlib-source-verification.json).

| Named set | a | b | deltaT (°C) | Declared mounting condition |
| --- | ---: | ---: | ---: | --- |
| open_rack_glass_glass | −3.47 | −0.0594 | 3 | Relatively free rear airflow |
| close_mount_glass_glass | −2.98 | −0.0471 | 1 | Limited/restricted rear airflow, e.g. roof mounting with a gap |
| open_rack_glass_polymer | −3.56 | −0.0750 | 3 | Free airflow; different construction |
| insulated_back_glass_polymer | −2.81 | −0.0455 | 0 | No rear airflow; different construction |

The function takes incident POA irradiance in W/m², ambient dry-bulb temperature in °C and **10-m-height wind in m/s**, and returns **cell temperature** in °C. It first models back-surface temperature, then adds `POA/reference_irradiance × deltaT`; the reference irradiance is 1000 W/m². These are representative construction/mounting models, not Trina-specific calibration. For the glass/glass reference module, the two corresponding sets can be offered as explicit declared scenarios; actual mounting/ventilation must still be chosen. The glass/polymer sets cannot silently stand in for an unprovided insulated glass/glass set. [Source inputs/equations/mounting definitions](https://github.com/pvlib/pvlib-python/blob/v0.16.1/pvlib/temperature.py#L57-L137), [verified values](raw/model-input-verification.json).

Unresolved by these sources: installed rear airflow and model calibration, site-specific optical/loss factors, real conversion/equipment limits, shading, and field accuracy. The Trina NOCT rating does not itself provide SAPM a/b/deltaT. Do not infer these from roof pitch alone, or present a declared reference scenario as manufacturer-validated yield.
